# V1 persistence and data-lifecycle policy

This document records the Phase P9 decisions for SQLite migrations, transcript retention,
memory records, and conversation summaries.

## Schema and migration policy

- The SQLite schema has an explicit `schema_version` table. V1 currently targets schema version 3.
- Pending migrations run in numeric order and are idempotent against the version recorded in the database.
- The complete pending migration chain for a startup runs inside one SQLite transaction. Any migration
  failure rolls the entire startup migration attempt back.
- V1 does **not** automatically create a second persistent database backup before migration. Such a
  copy could duplicate retained transcripts/memories or a legacy plaintext secret row and would make
  deletion semantics misleading. Users who want a manual backup can copy the application-data database
  while the application is stopped.
- Persistent database initialization or migration failure aborts application initialization. Production
  never silently substitutes an in-memory database.
- In-memory SQLite remains available only for explicit tests and other non-persistent test fixtures.

## Transcript policy

- Transcript persistence remains opt-in through `save_transcripts`.
- Only final `user` and `moose` transcript roles are accepted for storage. Partial-role values are rejected.
- Session IDs are trimmed and bounded to 128 characters; transcript text is trimmed and bounded to
  16,384 characters.
- Repeated delivery of the same consecutive final `(session, role, text)` record is idempotent rather than
  creating a duplicate row.
- At most 1,000 transcript rows are retained. IPC retrieval is capped at the 200 most recent records and
  returns that recent window in chronological order.
- Timestamps are generated by SQLite at persistence time and row IDs provide a stable tie-breaker/order.

## Memory-record policy

- V1 memory stores explicit semantic facts only; it does not automatically ingest transcripts, desktop
  observations, ambient events, or inferred summaries.
- New explicit facts are recorded with source `remember_fact` and confidence `1.0`.
- Migrated pre-P9 records retain source `legacy` with confidence `1.0`.
- Facts are trimmed and bounded to 1,024 characters; categories are trimmed and bounded to 64 characters.
- Records carry both `created_at` and `updated_at` timestamps.
- Remembering the same normalized fact again updates its category/source/confidence/`updated_at` metadata
  instead of silently creating another copy.
- Memory remains behind the existing `memory_enabled` privacy gate and `Forget Everything` continues to
  delete persisted memories and transcripts.

## Conversation-summary decision

V1 does **not** persist conversation summaries. No `conversation_summaries` table or background summarizer
is created. A persisted summary would introduce a new derived-private-data class without being required for
the V1 experience. V1 uses only explicitly enabled transcript retention and explicitly enabled semantic
memory. A future summary feature must define a separate privacy opt-in, bounded schema/retention policy,
delete semantics, and migration before it can be enabled.
