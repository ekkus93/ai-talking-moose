## 1. Purpose

Local LLM V1 is substantially implemented and has extensive automated, packaging, privacy, and real-model evidence. A later full source review of the merged implementation found several issues that were not represented in the original closure evidence. The most important are:

1. cancellation can be acknowledged while model SHA verification continues and the model can still be installed;
2. the required runtime diagnostics structure exists but is not reachable through production IPC/UI;
3. one generation request can observe settings from multiple moments, allowing provider/privacy/configuration races;
4. a profile written by a future settings schema can be destructively normalized by an older application;
5. installed GGUF contents are not re-hashed before later runtime use;
6. large synchronous hashing runs directly inside an async installation path;
7. frontend settings updates are expressed as complete snapshots, which permits stale callers to overwrite unrelated fields;
8. installer status and error diagnostics have smaller truthfulness defects;
9. HTTPS is guaranteed for the catalog URL but not explicitly for every redirect target;
10. chat-template ownership is more heuristic/application-owned than some comments and records imply;
11. several Local LLM source files are large enough that phase ownership is becoming difficult to reason about.

This specification converts those findings into explicit invariants and acceptance requirements. It does not invalidate the engineering value of the previous implementation or its historical evidence; instead it supersedes the affected closure claims where later review found a gap.

## 4. Product and Engineering Goals

### 4.1 Primary goals

1. Make installer cancellation truthful and effective in every UI-visible cancellable phase.
2. Ensure cancellation immediately before final promotion cannot install a cancelled artifact.
3. Keep expensive filesystem hashing off async executor workers.
4. Make installer phase/status diagnostics truthful across independent status refreshes.
5. Keep every redirect in a model download on HTTPS.
6. Make “verified installed artifact” mean the bytes used by the runtime still match the pinned catalog SHA, subject to an explicitly documented cache policy.
7. Expose runtime diagnostics through the same typed Rust -> generated contract -> TypeScript -> Tauri path used for other Local LLM IPC data.
8. Make each generation request use one immutable settings/provider snapshot.
9. Fail closed when an older application encounters a persisted settings version newer than it understands.
10. Replace stale full-object frontend settings writes with patch-oriented intent.
11. Clarify runtime cancellation and chat-template ownership rather than relying on misleading comments or unreachable hooks.
12. Add deterministic tests for every newly discovered failure mode.
13. Reduce high-risk module concentration where refactoring improves phase ownership without changing behavior.

### 4.2 Secondary goals

1. Keep Local LLM UI behavior responsive during verification and cancellation.
2. Improve diagnostics without exposing prompts, outputs, memories, credentials, or raw native errors.
3. Preserve existing model/runtime performance characteristics unless a change is required for correctness.
4. Preserve all current fail-closed behavior.

## 7. Required Cross-Cutting Invariants

The remediation is not complete until all of these invariants hold.

### 7.1 Cancellation invariant

If the application reports that cancellation was accepted for an active install, then that install MUST NOT later transition to `installed` unless the user explicitly starts a new install.

Cancellation MUST be observed:

- while receiving bytes;
- between download completion and verification;
- during SHA verification;
- after verification and before promotion;
- before writing the install marker.

After cancellation:

- no final GGUF is promoted;
- no valid install marker is written;
- staging files are cleaned up;
- status becomes a truthful non-installed state;
- a later explicit install can succeed cleanly.

### 7.2 Async blocking-work invariant

Large synchronous file hashing MUST NOT execute directly on the Tokio/Tauri async executor thread. Blocking verification must use a blocking worker or equivalent isolated execution context.

Cancellation responsiveness must remain bounded by the verification read chunk rather than the full artifact hash duration.

### 7.3 Artifact integrity invariant

A model may be described as **verified for runtime use** only when its current bytes have been cryptographically matched to the pinned catalog SHA under a documented cache policy.

A cached verification is acceptable if it is invalidated conservatively when file identity/metadata changes. Size plus marker metadata alone is not sufficient to claim current-byte verification.

### 7.4 Request consistency invariant

One logical generation request MUST use one immutable configuration snapshot for:

- text provider;
- provider-specific model selection;
- memory inclusion;
- transcript-retention decisions that apply to that request;
- relevant privacy gates;
- model/output policy inputs derived from settings.

A concurrent settings change may affect the **next** request, but MUST NOT partially rewrite the current request's provider/privacy/configuration semantics.

A post-generation privacy gate may still suppress delivery if the user disables behavior while generation is in flight; that is a second safety check, not a substitute for request-snapshot consistency.

### 7.5 Settings compatibility invariant

For persisted settings version `v` and application-supported version `CURRENT`:

```text
v < CURRENT  -> migrate deterministically
v == CURRENT -> load normally
v > CURRENT  -> fail closed as newer/incompatible settings
```

An older application MUST NOT deserialize-and-drop unknown future fields and then persist the result as an older schema.

### 7.6 Frontend write-intent invariant

A component changing one setting must express **only that intended patch**. It must not submit a stale complete `AppSettings` snapshot that can turn unrelated stale values into apparent user intent.

The store remains responsible for:

- constructing the complete candidate;
- serializing writes;
- rebasing queued changes;
- reconciling rejected writes;
- maintaining the last successfully persisted snapshot.

### 7.7 Diagnostics invariant

Local LLM diagnostics MUST be production reachable and truthful without exposing sensitive content.

At minimum runtime diagnostics must surface:

- selected local model ID;
- loaded model ID/revision/quantization;
- loaded/unloaded state;
- runtime phase;
- thread count;
- context size;
- generation-in-progress state;
- safe last-error category;
- last generation duration;
- prompt/output token counts when available;
- tokens/second when available.

Installer diagnostics must surface current install phase and a genuinely chronological last safe error.

### 7.8 Network invariant

Model download is the one explicit Local LLM network path. Every requested and redirected URL used for artifact bytes MUST remain HTTPS. A redirect to HTTP or another unsupported scheme MUST fail closed before artifact bytes are accepted.

### 7.9 Privacy invariant

No remediation may weaken existing protections against logging or exposing:

- API keys;
- prompts;
- typed user text;
- memories;
- transcripts;
- generated model output;
- raw native error strings containing paths/provider details.

New diagnostics must expose categories/metrics, not payload content.

## 8. Installer Remediation Design

### 8.1 Explicit in-flight record

Replace the current “token means in flight” representation with an installer-owned in-flight record that can represent at least:

```text
model_id
cancel_token
phase: downloading | verifying | promoting
started_at / sequence (if useful for diagnostics)
```

A status refresh must read this phase rather than synthesizing all active work as `downloading`.

### 8.2 Cancellable verification

The artifact verifier must accept cancellation state. The SHA loop must check cancellation at deterministic bounded intervals.

Recommended structure:

1. transition installer phase to `verifying`;
2. run the blocking hash worker;
3. worker checks cancellation once per read chunk;
4. worker returns typed `Cancelled`, `SizeMismatch`, `HashMismatch`, or verified result;
5. async caller checks cancellation again after worker completion;
6. only an uncancelled verified result may proceed to promotion.

The final cancellation check before promotion is mandatory even if the worker checked cancellation internally, because cancellation can race the worker's return.

### 8.3 Atomic promotion ordering

Promotion must retain the existing staging/final atomicity rules. The intended ordering is:

```text
download staging artifact
-> verify staging bytes
-> final cancellation check
-> atomically promote artifact
-> final cancellation/consistency check as appropriate
-> atomically persist validated marker
-> publish installed state
```

If cancellation occurs after a rename but before a valid marker is committed, cleanup must leave the model non-installed and safe on restart.

### 8.4 HTTPS redirect policy

Use a redirect policy that:

- limits redirect count;
- rejects a target whose scheme is not `https`;
- does not silently downgrade HTTPS to HTTP;
- returns a safe installer/network error.

Tests must not require public Internet access; redirect behavior can be exercised with local test servers/constructed redirect attempts where supported by the test harness.

### 8.5 Chronological errors

Do not derive “last error” from `HashMap` iteration order. Maintain either:

- one dedicated latest safe error record with monotonic sequence/time; or
- per-model errors plus a monotonic sequence and select by that sequence.

Normal diagnostics must never expose raw underlying error strings.

### 8.6 Runtime-use re-verification

Before first runtime load in a process, verify current GGUF contents against the catalog SHA unless an equally strong verification result is already cached for that exact file identity.

A practical V1 policy is:

- installation verification remains authoritative at install time;
- runtime manager performs one content hash before first load per process;
- successful verification is cached using canonical path plus conservative file metadata/identity;
- cache invalidates if identity/size/mtime or equivalent observed metadata changes;
- any mismatch fails closed and the model is not loaded.

The implementation must not hash on every token generation.

### 8.7 Installer module structure

The current installer module owns transport, state, path policy, hashing, promotion, deletion, and diagnostics. Refactoring is encouraged where it makes the above invariants mechanically obvious.

A reasonable split is:

```text
installer/
  mod.rs
  state.rs
  download.rs
  verify.rs
  paths.rs
  promote.rs
  delete.rs
  diagnostics.rs
  tests/...
```

Exact filenames are not mandated. The requirement is coherent ownership and no duplicated policy.

## 9. Runtime Diagnostics Completion

### 9.1 Existing runtime diagnostics are the source of truth

Do not create a parallel hand-maintained diagnostics implementation if `LocalRuntimeManager::diagnostics()` already owns the required runtime state. Make that path production reachable.

### 9.2 IPC shape

The frontend-visible Local LLM diagnostics response should combine or clearly compose:

```text
installer diagnostics
runtime diagnostics
```

The response must be represented through:

1. Rust serializable types;
2. the generated frontend contract representative data;
3. TypeScript interfaces/shape checking;
4. the Tauri command dispatcher fixture;
5. production frontend diagnostics rendering.

Do not add an unverified handwritten JSON tunnel around the existing contract system.

### 9.3 Diagnostics UI

Diagnostics may live in the existing Local LLM settings panel or the application diagnostics surface. It must be understandable without reading logs and must not display sensitive prompt/output text.

At minimum show useful runtime identity/state/performance fields and the current installer phase/error category.

## 10. Settings Version Compatibility

### 10.1 Future-version rejection

`AppSettings::from_persisted_json()` or its successor must inspect the persisted version before normalizing it.

A future-version profile must return a typed safe startup/settings compatibility error. It must not:

- silently use defaults;
- normalize the future version down to current;
- persist a stripped representation;
- delete unknown fields.

### 10.2 Migration tests

Preserve all existing older-version migration behavior. Add a fixture with:

- `settings_version = CURRENT + 1`;
- at least one unknown future field;
- recognizable existing fields.

The test must prove startup/load fails closed and the persisted JSON is not rewritten.

## 11. Per-Request Settings Snapshot

### 11.1 Snapshot ownership

At the start of ambient or typed text generation, capture one settings snapshot. Provider/model creation must derive from that snapshot instead of independently re-reading global settings later.

Preferred direction:

```rust
let request_settings = state.settings_snapshot();
let model = state.get_text_model_for(&request_settings)?;
```

The exact API may differ, but provider selection must not perform another mutable-settings read.

### 11.2 Privacy and memory

Prompt memories, transcript policy, active privacy conditions, and provider selection used to construct/send the request must be computed from the same snapshot.

A post-generation current-state check remains appropriate for “do not speak/show this anymore” behavior.

### 11.3 Concurrency proof

Tests must use synchronization barriers/deferred futures to force a settings change between:

1. request snapshot acquisition; and
2. provider invocation.

They must prove the in-flight request remains internally consistent and the next request uses the new settings.

---

## 12. Frontend Settings Write API

### 12.1 Patch-oriented intent

Replace component-facing complete-object updates for ordinary setting edits with patch-oriented calls such as:

```ts
updateSettingsPatch({ text_provider: provider })
```

or an equivalent typed partial intent API.

### 12.2 Store remains authoritative

The store must merge a patch onto its authoritative reconciled base. Existing serialization/rebase/error-reconciliation guarantees from V1R-216/V1R-217 must remain intact.

### 12.3 Migration of callers

Migrate settings components away from patterns such as:

```ts
updateSettings({ ...settings, field: value })
```

where the complete object is not semantically required.

Any remaining complete-object replacement API must have an explicit use case and tests showing why replacement rather than patching is correct.

## 13. Runtime Cancellation Semantics

The local runtime already has cooperative cancellation internally. The remediation must decide and document whether normal application generation needs an externally controllable cancellation handle.

Minimum requirement:

- do not claim user/application cancellability for a path whose `TextModel::generate()` call always owns an unreachable private token;
- preserve cooperative checks between decode iterations;
- preserve bounded shutdown behavior;
- if current product behavior needs cancellation (for example provider switch, shutdown, or future typed cancellation), wire a manager-owned/request-owned handle rather than unsafe native abort FFI.

This task is primarily semantic/API cleanup unless a concrete application cancellation requirement is identified by source behavior.

## 14. Chat Template Ownership

### 14.1 Truthful documentation

The code and docs must accurately describe the current design:

- the GGUF embedded template is inspected/validated for supported model-family compatibility;
- application code applies deterministic family-specific framing where the chosen binding cannot safely execute the full embedded template semantics;
- Qwen non-thinking behavior is enforced explicitly;
- unsupported or unexpected template shapes fail closed.

Do not state that llama.cpp directly applies the embedded template if the application is actually rendering family-specific ChatML itself.

### 14.2 Stronger template identification

Substring checks may remain only if they are demonstrated sufficient for the two pinned artifacts and documented as such. Prefer a normalized template fingerprint or another deterministic compatibility discriminator if it can be implemented without adding a disproportionate framework/dependency.

Any change to actual prompt framing for the pinned models requires rerunning the relevant P12 real-model acceptance.

## 15. Required Tests and Negative Probes

At minimum the remediation test suite must add deterministic coverage for:

1. cancel while downloading -> no install;
2. cancel after download before verify -> no install;
3. cancel during SHA verification -> no install;
4. cancel after verification before promotion -> no install;
5. cancellation cleanup permits a later successful reinstall;
6. verification work runs through the blocking-work boundary;
7. status query reports `verifying` while verification is active;
8. last installer error is chronologically latest;
9. HTTPS -> HTTP redirect is rejected;
10. same-size post-install GGUF mutation is rejected before runtime load;
11. unmodified verified artifact can still load without hashing on every generation;
12. persisted future settings version fails closed and is not rewritten;
13. concurrent settings change cannot split one request across provider/privacy snapshots;
14. the next request observes the new settings;
15. stale frontend component snapshot cannot overwrite an unrelated newer setting after patch-API migration;
16. runtime diagnostics command returns live runtime fields through production IPC fixtures;
17. runtime diagnostics contain no prompt/output sentinel;
18. Cancel UI does not report success while the backend later reports the same operation installed;
19. generated frontend contract detects diagnostics-shape drift;
20. command registration guard covers any newly added/changed diagnostics command.

Existing tests that cover the same invariant may be extended instead of duplicated.
