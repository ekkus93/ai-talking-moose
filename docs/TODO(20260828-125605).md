## Tracker rules

- `[x]` means the criterion is implemented **and** supported by evidence appropriate to the claim.
- **No row may be closed on a green CI run alone.** `V1R-210` establishes that CI and a clean local checkout currently disagree about the frontend toolchain. Every closure must state which environment produced its evidence.
- Tests must exercise the production path. A test that duplicates a production branch instead of calling it — a Rust `#[cfg(test)]` mirror, or a frontend fallback branch standing in for IPC — satisfies nothing here.
- Flake claims require a **measured** rate over a stated number of runs, not a single green run.
- Records corrections (`V1R-217`) are not implementation work and must not be reported as such.
- Manual, physical-device, packaging, and release evidence stays distinct from automated CI. This plan adds no manual acceptance obligation and converts none of the existing ones.

## Sequencing

Work in ID order. The dependency is real, not stylistic:

1. **`V1R-210` first.** Until `npm run check:all` runs to completion, no other item in this plan can be verified, and every "the suite passes" claim is evidence about Vitest 2.1.9 rather than the declared 4.1.11.
2. **`V1R-211` second.** Until the Rust gate is deterministic, a green run does not distinguish "fixed" from "lucky."
3. **`V1R-212` third.** It is expected to break existing frontend tests. That breakage is the finding, and it needs a trustworthy gate to be legible.
4. The remainder may proceed in any order.

# P22 — Test fidelity

## V1R-212 — Frontend tests must exercise the IPC boundary — **S2**

`isTauri()` (`src/lib/tauriBridge.ts:30-35`) reads `window.__TAURI_INTERNALS__`, which **nothing in `src/` ever sets**. Every frontend test therefore takes the browser fallback branch in all forty bridge methods, returning before `await import("@tauri-apps/api/core")`. The command dispatcher at `src/test/setup.ts:9-62` and the event stub at `:64-68` are unreachable. No test asserts on `invoke`. Spec §6.1.

This is the frontend form of the defect `V1R-180` closed in Rust: the suite proves properties of a parallel implementation.

- [ ] Make frontend tests run the production branch — set `__TAURI_INTERNALS__` in `src/test/setup.ts`, or restructure `tauriBridge` so the fallback is not selected by ambient global state.
- [ ] Keep `invoke` mocked at the module boundary so tests stay offline and hardware-free.
- [ ] Add a test that fails if the suite silently reverts to the fallback branch.
- [ ] Extend `src/test/setup.ts`'s dispatcher to cover every command the suite reaches. It currently enumerates 15 and returns `null` for the rest.
- [ ] Each fixture must match the real Rust command's argument and return shape. Cite the `#[tauri::command]` it mirrors.
- [ ] Decide the fallback branch's fate: keep it as an explicitly tested browser-only affordance, or remove it. Record which and why.

### Expected breakage

Enabling the production branch is expected to fail existing tests. That is the previously hidden gap surfacing, not a regression.

- [ ] Enumerate every test that breaks, with its cause.
- [ ] Resolve each by supplying a correct fixture — **not** by re-widening the fallback or loosening an assertion.
- [ ] For any failure that reveals a genuine frontend/backend contract mismatch, record it as a finding in its own right.

### Acceptance

- [ ] `invoke` is demonstrably called during the suite, asserted by at least one test.
- [ ] A deliberate rename of a Rust `#[tauri::command]` causes a frontend test failure. Demonstrate this, then revert.
- [ ] The full frontend suite passes on the reconciled toolchain from `V1R-210`.

## V1R-216 — Fix the settings persistence race — **S3**

`updateSettings` (`src/stores/mooseStore.ts:276-280`) sets store state **after** awaiting IPC; `updateSettingsContinuous` (`:282-289`) sets it immediately and debounces the write by 100 ms (`:18`). `BehaviorTab.tsx` uses both on one screen — checkboxes via the former, the Talkativeness slider (`:44-49`) and comments-per-hour slider (`:69-75`) via the latter. Spec §7.1.

Reachable interleaving: toggle a checkbox → during the await, drag a slider → the await resolves and overwrites the slider value, which visibly snaps back → 100 ms later the slider value is persisted anyway. The store then shows one value while the backend holds another.

- [ ] Ensure a continuous edit made during an in-flight discrete write is not discarded.
- [ ] Ensure the store's settings cannot diverge from what was persisted.
- [ ] Preserve the existing behavior that continuous controls feel immediate and do not persist every pointer movement.
- [ ] Confirm the fix holds for the reverse order — a discrete write starting while a continuous write is pending.

### Acceptance

- [ ] A deterministic test exercises the step-2 interleaving, not merely sequential calls.
- [ ] A test asserts the store and the last persisted snapshot agree after the interleaving.
