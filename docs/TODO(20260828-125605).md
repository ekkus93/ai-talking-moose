## Tracker rules

- `[x]` means the criterion is implemented **and** supported by evidence appropriate to the claim.
- **No row may be closed on a green CI run alone.** `V1R-210` establishes that CI and a clean local checkout currently disagree about the frontend toolchain. Every closure must state which environment produced its evidence.
- Tests must exercise the production path. A test that duplicates a production branch instead of calling it — a Rust `#[cfg(test)]` mirror, or a frontend fallback branch standing in for IPC — satisfies nothing here.
- Flake claims require a **measured** rate over a stated number of runs, not a single green run.
- Records corrections (`V1R-218`) are not implementation work, must not be reported as such, and must not manufacture product scope from a misread criterion.
- Manual, physical-device, packaging, and release evidence stays distinct from automated CI. This plan adds no manual acceptance obligation and converts none of the existing ones.

## V1R-212 — Frontend tests must exercise the IPC boundary — **S2**

`isTauri()` (`src/lib/tauriBridge.ts:30-35`) reads `window.__TAURI_INTERNALS__`, which **nothing in `src/` ever sets**. Every frontend test therefore takes the browser fallback branch in all forty bridge methods, returning before `await import("@tauri-apps/api/core")`. The command dispatcher at `src/test/setup.ts:9-62` and the event stub at `:64-68` are unreachable. No test asserts on `invoke`. Spec §6.1.

This is the frontend form of the defect `V1R-180` closed in Rust: the suite proves properties of a parallel implementation.

**Amended — acceptance narrowed.** The original criterion required that renaming a Rust `#[tauri::command]` break a frontend test. Setting `__TAURI_INTERNALS__` and mocking `invoke` cannot deliver that: command names are hard-coded strings in `tauriBridge.ts`, and the mock dispatcher holds its own independent copies, so both sides still agree after a Rust rename. That concern moved to `V1R-213`.

- [ ] Make frontend tests run the production branch — set `__TAURI_INTERNALS__` in `src/test/setup.ts`, or restructure `tauriBridge` so the branch is not selected by ambient global state.
- [ ] Keep `invoke` mocked at the module boundary so tests stay offline and hardware-free.
- [ ] Add a test that fails if the suite silently reverts to the fallback branch.
- [ ] Extend `src/test/setup.ts`'s dispatcher to cover every command the suite reaches. It currently enumerates 15 and returns `null` for the rest.
- [ ] Each fixture must match the real Rust command's argument and return shape. Cite the `#[tauri::command]` it mirrors.

### Expected breakage

Enabling the production branch is expected to fail existing tests. That is the previously hidden gap surfacing, not a regression.

- [ ] Enumerate every test that breaks, with its cause.
- [ ] Resolve each by supplying a correct fixture — **not** by re-widening the fallback or loosening an assertion.
- [ ] For any failure that reveals a genuine frontend/backend contract mismatch, record it as a finding in its own right.

### Acceptance

- [ ] `invoke` is demonstrably called during the suite, asserted by at least one test.
- [ ] A test fails if the suite reverts to the fallback branch. Demonstrate, then revert.
- [ ] The full frontend suite passes on the reconciled toolchain from `V1R-210`.

## V1R-213 — Verify the Rust↔frontend command contract — **S2**

**Added** from external review, carrying the acceptance property `V1R-212`'s mechanism cannot provide. Spec §6.2.

The frontend invokes command names as string literals; Rust registers them in `tauri::generate_handler!` (`src-tauri/src/lib.rs:181-222`). Nothing connects the two, so a rename, signature change, or removed registration is detectable only at runtime in the packaged app.

Verified current state — no defect exists today, which makes this the right moment to add the gate:

- [ ] Add a check that fails when a frontend-invoked command name is not registered in Rust.
- [ ] Satisfy it by one of: generated IPC bindings emitted from the Rust command registry, or a CI verifier extracting registered names and comparing them against frontend usage or a shared manifest.
- [ ] Report registered-but-uninvoked commands informationally. Backend-initiated commands are legitimate and must not fail the check.
- [ ] Note the four commands registered via qualified paths (`commands::character::set_mute`, `commands::character::cancel_standalone_speech`, `commands::conversation::start_conversation`, `commands::conversation::barge_in`) — a naive line-based extractor misses them.
- [ ] Confirm the check needs no Google credential, no network, and no audio hardware.
- [ ] Document it in `AGENTS.md`.

# P23 — Runtime and record correctness

## V1R-216 — Order settings writes so delayed writes cannot clobber newer state — **S3**

`updateSettings` (`src/stores/mooseStore.ts:276-280`) sets store state **after** awaiting IPC; `updateSettingsContinuous` (`:282-289`) sets it immediately and debounces the write by 100 ms (`:18`). `BehaviorTab.tsx` uses both on one screen — checkboxes via the former, the Talkativeness slider (`:44-49`) and comments-per-hour slider (`:69-75`) via the latter. Spec §7.1.

Reachable interleaving: toggle a checkbox → during the await, drag a slider → the await resolves and overwrites the slider value, which visibly snaps back → 100 ms later the slider value is persisted anyway. The store then shows one value while the backend holds another.

**Amended — invariant narrowed.** The original row required that the store "cannot diverge from persisted state." A second divergence path exists independently of ordering, so that invariant is broader than an ordering fix can deliver. It moved to `V1R-217`.

- [ ] Ensure a continuous edit made during an in-flight discrete write is not discarded.
- [ ] Ensure an older delayed write cannot overwrite newer state.
- [ ] Preserve the existing behavior that continuous controls feel immediate and do not persist every pointer movement.
- [ ] Confirm the fix holds for the reverse order — a discrete write starting while a continuous write is pending.

### Acceptance

- [ ] A deterministic test exercises the step-2 interleaving, not merely sequential calls.
- [ ] A test covers the reverse ordering.
- [ ] After any successful-write interleaving, the store matches the last persisted snapshot.

## V1R-217 — Reconcile the store when a settings write is rejected — **S3**

**Added** from external review, carrying the invariant removed from `V1R-216`. Spec §7.2.

`scheduleContinuousSettingsWrite` swallows persistence failure (`src/stores/mooseStore.ts:40-43`):

```ts
void tauriBridge.updateSettings(pending).catch(() => {
  // The next explicit settings action or reload reconciles persistence. Keep
  // provider/backend error details out of the frontend console.
});
```

The optimistic value set at `:285` stays in the store. On backend rejection — validation failure, secure-store unavailability, persistence error — the user sees a setting that was never saved, with no indication, and the next write computes its payload from a state the backend never accepted.

Keeping provider error detail out of the frontend is correct and must be preserved. Silently discarding the *fact* of failure is the defect.

- [ ] Choose and implement a recovery: rollback the optimistic value, re-read authoritative persisted settings, or surface a typed non-sensitive error while the store reconciles.
- [ ] Ensure subsequent writes do not compute their payload from a falsely assumed persisted base.
- [ ] Keep provider/backend error detail out of the frontend console — no message, URL, or credential fragment.
- [ ] Apply the same treatment to the discrete `updateSettings` path if it can also reject.

### Acceptance

- [ ] A test injects a rejected write and asserts the store does not retain the unpersisted value.
- [ ] A test asserts no backend error detail reaches the console.
- [ ] A test asserts the next write is computed from a reconciled base.
