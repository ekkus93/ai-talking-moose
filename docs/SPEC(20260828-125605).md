## 1. Purpose

A source-level code review conducted on 2026-08-28 against `HEAD = 55bcea5c`, together with an execution of the repository's canonical quality gate, produced eight confirmed defects. This document specifies the required end state for each.

The prior remediation cycle (P14–P20) repaired the defects it set out to repair. This cycle addresses a different and narrower class of problem: **the repository's own verification apparatus cannot currently be trusted to tell the truth about the repository.**

Three independent mechanisms were found, each of which causes a gate to report a result that does not correspond to the state of the code:

1. **The gate does not run.** `npm run check:all` exits non-zero on a clean checkout for reasons unrelated to the source under test (§4).
2. **The gate is nondeterministic.** `npm run check:rust` fails approximately one run in five, on a test whose failure carries no information about the code it names (§5).
3. **The gate tests a parallel implementation.** The entire frontend test suite exercises browser fallback mocks rather than the IPC boundary those mocks stand in for (§6).

The third mechanism is the same class of defect that `V1R-180` closed on the Rust side — a test that duplicates a production branch rather than calling it. It survived that remediation because `V1R-180` was scoped to `#[cfg(test)]` mirrors in Rust and the frontend equivalent is expressed differently: as a runtime environment check, not a compile-time attribute.

Every finding in this document was **verified against source or by measurement**, and each requirement cites its evidence. Claims that were formed during review but could not be confirmed are recorded in §10 as unverified rather than promoted to requirements. This distinction is load-bearing: §5 in particular specifies a requirement whose *observable defect* is measured and whose *mechanism* is not yet established, and the requirement is written so that it cannot be closed by fixing the hypothesis alone.

## 3. Severity model

This document retains the severity model established in `SPEC(20260824-142233).md` §3, with one clarification for this cycle's subject matter.

- **S1 — Correctness under concurrency or failure.** A race, panic, silent data loss, or stuck state that can occur in normal operation. Must be fixed before V1. **For this cycle, a gate that fails or flakes for reasons unrelated to the code under test is S1**, because it destroys the signal every other requirement in the repository depends on.
- **S2 — Privacy or test-integrity defect.** A privacy control whose enforcement is unproven, or a test that cannot fail when its production path regresses. Must be fixed before V1, because these defects hide other defects.
- **S3 — User-visible defect.** Incorrect or misleading behavior a user can observe, including accessibility barriers. Must be fixed before V1.
- **S4 — Structural.** Duplication, dead code, or record divergence that has not yet produced a user-visible defect but has already caused drift or blocks safe change. Fix before V1 where cheap; otherwise record an explicit deferral.

A requirement is complete only when its runtime behavior is correct **and** a test exercises the production path. A test that duplicates a production branch instead of calling it does not satisfy any requirement in this document.

**Additional closure rule for this cycle.** No requirement in this document may be closed on the basis of a green CI run alone, because §4 establishes that CI and a local clean checkout currently disagree. Closure evidence must state which environment produced it.

## 4. Gate executability (P21)

### 4.1 Committed `node_modules/` has diverged from the lockfile — **S1**

This repository tracks `node_modules/` in git (12,845 files under `git ls-files node_modules`). Commit `2d61e7b5` (`build: eliminate development dependency advisories`) upgraded the frontend toolchain in `package.json` and `package-lock.json`, and changed `vite.config.ts:26` to `minify: "oxc"`, but did not update the tracked `node_modules/` tree.

Measured divergence:

| Package | `package.json` | `package-lock.json` | Tracked `node_modules/` |
| --- | --- | --- | --- |
| `vite` | `^8.2.2` | 8.2.2 | **5.4.21** |
| `vitest` | `^4.1.11` | 4.1.11 | **2.1.9** |
| `@vitejs/plugin-react` | `^6.1.0` | 6.1.1 | **4.7.0** |
| `esbuild` | — | **absent** | **0.21.5** |

The tracked version is confirmed by `git show HEAD:node_modules/vite/package.json`, so this is committed state, not local drift.

Three consequences follow, each independently sufficient to require repair:

1. **The canonical gate does not run.** `npm run check:all` exits 2 at its first step:
   ```
   vite.config.ts(26,5): error TS2769: No overload matches this call.
     Type '"oxc"' is not assignable to type 'boolean | "terser" | "esbuild" | undefined'.
   ```
   `minify: "oxc"` requires Vite 7 or later. Vite 5 can neither type it nor execute it. `npm run build` fails identically. Three of the five frontend gate steps therefore cannot report on the source at all.

2. **CI and a clean checkout disagree.** Every CI job runs `npm ci` first (`.github/workflows/ci.yml:44,135,169,236`), which installs the lockfile tree and passes. A developer who clones the repository and runs the documented command in `AGENTS.md` gets a failure that has nothing to do with their change. The repository's stated verification workflow is not reproducible.

3. **`V1R-006` is not satisfied.** That task is recorded `[x]` in `TODO(20260818-163801).md:89-97` with implementation evidence asserting that the advisory-bearing development dependency chain was eliminated. `esbuild` 0.21.5 remains committed in the repository and is absent from `package-lock.json` entirely. CI's `npm audit` runs after `npm ci` and therefore never observes it. This is the single reopened item from a prior remediation cycle.

A fourth consequence is not a defect but must be recorded because it invalidates evidence: **the 64 frontend tests observed passing during review ran under Vitest 2.1.9**, not the 4.1.11 the project's records assert. Any prior claim of the form "the frontend suite passes" is evidence about a toolchain the project no longer declares.

**Required end state.** The tracked `node_modules/` tree, `package-lock.json`, and `package.json` are mutually coherent. `npm run check:all` completes every step on a clean checkout with no install step. No package is present in the tracked tree that is absent from the lockfile. `V1R-006`'s claim is either true of the tracked tree or its record is corrected.

**Explicitly out of scope.** Whether `node_modules/` *should* be tracked at all is not decided here. `CLAUDE.md` records that its committed state "looks like an oversight, not a convention" and instructs that it not be changed unprompted. This requirement makes the existing arrangement coherent; it does not adopt or abandon it. If the project later decides to untrack `node_modules/`, that decision supersedes this requirement's mechanism but not its acceptance criterion.

### 4.2 Gate coherence is not itself verified — **S2**

The divergence in §4.1 persisted across at least one full remediation cycle without detection, because nothing compares the tracked tree to the lockfile. CI cannot detect it by construction: `npm ci` deletes and replaces `node_modules/` before any check runs, so CI never observes the committed tree.

**Required end state.** A check exists that fails when the tracked `node_modules/` tree diverges from `package-lock.json`, and it runs in an environment that does not first overwrite the tree. The check must fail on the §4.1 state and pass after it is repaired. A check that can only run after `npm ci` does not satisfy this requirement.

## 5. Gate determinism (P21)

### 5.1 `sensitive_asr_payloads_are_processed_without_entering_tracing` is nondeterministic — **S1**

**Measured:** 2 failures in 10 consecutive `cargo test --manifest-path src-tauri/Cargo.toml --all-features --lib` runs. The same test passes when run in isolation by name.

```
thread '...' panicked at src/asr/pipeline_tests.rs:552:5:
assertion failed: logs.contains("Local ASR inference worker started")
```

`npm run check:rust` is the declared source of truth for the Rust quality gate (`AGENTS.md`). It exits 101 on approximately one run in five for a reason unrelated to any change under test. The observed failure was reproduced during review at `HEAD = 55bcea5c` with a clean working tree.

**Structural hazard, independent of the flake.** The failing assertion at `pipeline_tests.rs:552` is the test's *positive control* — it proves that log capture is working before the test draws any conclusion from the absence of sensitive strings. The three assertions that follow it are the privacy assertions:

```rust
assert!(logs.contains("Local ASR inference worker started"));   // positive control
assert!(!logs.contains(TRANSCRIPT));
assert!(!logs.contains(std::str::from_utf8(RAW_PCM).unwrap()));
assert!(!logs.contains(&pcm_base64));
```

Whenever the condition that breaks the control is present, all three privacy assertions pass **vacuously** — an empty log contains no transcript. The control is therefore load-bearing for the privacy claim, and it is correct that it exists. The defect is not that the control fires; it is that the condition making it fire occurs at random in ordinary test runs, which both reddens CI and means that on any given run the privacy proof may be resting on a control that only happened to hold.

This pattern is not unique to this test. Six tests in the repository are privacy proofs of the form "sensitive value must not appear in logs," and every one of them passes vacuously if log capture silently yields nothing. Four use `capture_logs` (`src-tauri/src/test_support.rs:34-44`); two construct an equivalent subscriber inline. Half carry a positive control:

| Test site | Positive control |
| --- | --- |
| `asr/pipeline_tests.rs:511` | Yes — `:552`, and it is the assertion that flakes |
| `desktop/runtime.rs:289` | Yes — `assert!(logs.contains("Desktop observer result"))` |
| `ai/google/auth.rs:92` (inline subscriber) | Yes — `assert!(logs.contains("Google provider failure"))` |
| `character/prompt.rs:185` | **None** — only negative assertions |
| `commands/conversation/tests.rs:73` | **None** — only negative assertions |
| `tools/router/tests.rs:249` (inline subscriber) | **None** — only negative assertions |

The three without a control cannot distinguish "the sensitive value was correctly absent" from "nothing was captured at all," and would pass silently under the same condition that makes `pipeline_tests.rs:552` fail loudly.

**Leading hypothesis, not established.** `capture_logs` uses `tracing::subscriber::with_default`, which installs a subscriber **thread-locally**, while `tracing`'s callsite-interest and maximum-level caches are **process-global**. The six subscribers above are built concurrently by the parallel test harness, and two of them — `tools/router/tests.rs:249` and `ai/google/auth.rs:92` — omit the `.with_max_level(tracing::Level::TRACE)` that `capture_logs` sets, defaulting to `INFO`. If one of those wins a global interest recomputation at the moment the `debug!` at `asr/pipeline.rs:352` is first registered, that callsite is cached as disabled for the remainder of the process.

**This hypothesis is unconfirmed.** A narrowed reproduction restricted to those three tests produced 0 failures in 12 runs (§10.1). The hypothesis is recorded to direct investigation, not to define the fix.

**Required end state.** `npm run check:rust` is deterministic. The stated acceptance is a measured failure rate, not a code change:

- The full Rust suite completes with 0 failures across at least 20 consecutive runs on the same commit.
- Every log-capture privacy test carries a positive control proving capture was live, so that no privacy assertion in the repository can pass vacuously.
- If the fix is to make log capture robust rather than to serialize the tests, that robustness is itself tested.

Closing this requirement by fixing only the two divergent `with_max_level` calls, without the measured run, does not satisfy it. The mechanism may be something else.

## 6. Test fidelity (P22)

### 6.1 The frontend suite never exercises the IPC boundary — **S2**

`src/lib/tauriBridge.ts` implements every backend call as a two-branch function:

```ts
async getMicrophonePermission(): Promise<MicrophonePermissionState> {
  if (!isTauri()) return "unavailable";
  const { invoke } = await import("@tauri-apps/api/core");
  return invoke<MicrophonePermissionState>("get_microphone_permission");
},
```

There are exactly forty such branches. `isTauri()` (`src/lib/tauriBridge.ts:30-35`) reads `window.__TAURI_INTERNALS__`.

**Nothing in `src/` ever sets `__TAURI_INTERNALS__`** — not `src/test/setup.ts`, not any individual test, not the Vitest configuration. The only occurrences of that identifier in the repository are its two uses inside `isTauri()` itself.

Therefore, in every frontend test:

- `isTauri()` returns `false`;
- every bridge method returns its browser fallback mock and returns **before** reaching `await import("@tauri-apps/api/core")`;
- because that import is inside the branch, the mocked module is never even loaded;
- the `vi.mock("@tauri-apps/api/core")` command dispatcher at `src/test/setup.ts:9-62`, which maps 15 command names to fixtures, is unreachable for every `tauriBridge` method;
- the `vi.mock("@tauri-apps/api/event")` listener stub at `src/test/setup.ts:64-68` is likewise unreachable, since `tauriBridge.ts:228` short-circuits with `return () => undefined`.

No test in `src/test/` asserts on `invoke` at all, so nothing detects this.

This is the frontend expression of the defect `V1R-180` closed in Rust: a test suite proving properties of a parallel implementation rather than of the production path. The consequences are concrete. A command renamed in Rust, a changed argument shape, a changed return type, or a removed `#[tauri::command]` registration produces no frontend test failure. Every P11 and P12 frontend acceptance row in `TODO(20260818-163801).md` currently rests on this suite.

**Required end state.** Frontend tests exercise the production branch of `tauriBridge` — the branch that resolves `invoke` — with `invoke` mocked at the module boundary. The browser fallback branch is either separately and explicitly tested as a browser-only affordance, or removed. A test exists that fails if the suite silently reverts to the fallback branch.

**Expected consequence, which is the finding.** Enabling the production branch is expected to break existing tests, because `src/test/setup.ts`'s dispatcher returns `null` for any command it does not enumerate and currently enumerates 15. That breakage is the previously hidden gap, not a regression introduced by the fix. Each resulting failure must be resolved by supplying a fixture that matches the Rust command's real signature — not by re-widening the fallback.

### 6.2 The generated backend contract has no drift gate — **S2**

`V1R-060`'s duplicated-defaults defect was repaired correctly in substance: the hand-maintained `AppSettings` blob in `src/lib/tauriBridge.ts` is gone, and `src/lib/backendContract.ts` now derives frontend defaults, the Google model catalog, and the TTS voice catalog from `src/generated/backendContract.json`, which is produced from Rust by `scripts/generate_frontend_contract.sh`.

The generated file is committed, and **nothing regenerates it and verifies it is unchanged**. The script is referenced only by `package.json:14` (`generate:frontend-contract`); it appears nowhere in `.github/workflows/`. `src/test/backendContract.test.ts` asserts internal consistency of the committed JSON — that default model ids appear in the committed catalog, that the voice list has 30 entries — but nothing compares it to Rust.

The divergence this closes can therefore silently return: a changed Rust default, model id, or voice list leaves the committed JSON stale, and the frontend continues to assert against the stale copy. The failure mode is identical to the original `V1R-060` defect; only its location moved, from a hand-written blob to a generated-but-unverified file.

**Required end state.** CI regenerates `src/generated/backendContract.json` from Rust and fails if the committed file differs. The check must fail when a Rust default is changed without regenerating.

### 6.3 Browser fallback mocks report success — **S3**

Two fallback branches in `src/lib/tauriBridge.ts` return affirmative results for operations that did not occur:

- `hasGoogleApiKey()` returns `true` (`:249`), asserting a credential exists when no secure store was consulted.
- `testAiConnection()` returns `{ success: true, message: "Mock API connection successful!" }` (`:255-257`), reporting a successful provider connection with no connection attempted.

These are unreachable inside the packaged Tauri application, where `__TAURI_INTERNALS__` is always present, so this is not a shipping-behavior defect. It is recorded at S3 for two reasons. First, `hasGoogleApiKey()` gates onboarding (`src/stores/mooseStore.ts:255-273`), so a fail-open value on that path suppresses the privacy explanations. Second, these mocks are the values the entire suite in §6.1 currently asserts against, which is how a test suite comes to certify a connection test that has never connected.

**Required end state.** No fallback branch reports success for an operation that did not occur. Fallbacks for credential presence and connectivity checks fail closed or are removed with the branch.

## 7. Runtime and record correctness (P23)

### 7.1 Settings persistence race discards in-flight continuous edits — **S3**

`src/stores/mooseStore.ts` writes settings by two paths with different ordering:

- `updateSettings` (`:276-280`) cancels any pending debounced write, awaits the IPC call, and **then** calls `set({ settings: newSettings })`.
- `updateSettingsContinuous` (`:282-289`) calls `set({ settings: newSettings })` immediately and schedules the persistence write 100 ms later (`CONTINUOUS_SETTINGS_WRITE_DELAY_MS`, `:18`).

`src/components/Settings/BehaviorTab.tsx` uses both on the same screen: checkboxes call `updateSettings`, while the Talkativeness slider (`:44-49`) and the maximum-comments-per-hour slider (`:69-75`) call `updateSettingsContinuous`.

Reachable interleaving:

1. The user toggles a checkbox. `updateSettings(A)` cancels any pending write and awaits the IPC round trip.
2. During that await, the user drags the Talkativeness slider. `set({ settings: B })` applies immediately; a write of `B` is scheduled.
3. The IPC call resolves. `set({ settings: A })` overwrites `B`. **The slider visibly snaps back to its previous position.**
4. 100 ms later the scheduled write persists `B`.

The end state is that the store displays `A` while the backend holds `B`. The UI and persisted settings disagree until the next explicit reload, and the user's slider movement appears to have been rejected while in fact it was saved.

**Required end state.** A continuous edit made during an in-flight discrete settings write is not discarded, and the store's view of settings does not diverge from what was persisted. A deterministic test exercises the interleaving in step 2 — not merely sequential calls.

### 7.2 `min_cooldown_seconds` has no settings mapping — **S4**

`BehaviorConfig::min_cooldown_seconds` is initialized from the constant `V1_MIN_AMBIENT_COOLDOWN_SECONDS` (`src-tauri/src/character/personality.rs:80,92`) and consumed by the cooldown policy (`character/behavior.rs:133`, `character/cooldown.rs:200`). `AppSettings::apply_to_character_config` (`src-tauri/src/app/state.rs:186-201`) maps seven personality fields and five behavior fields; `min_cooldown_seconds` is not among them, and no corresponding field exists in `AppSettings`.

This is the sole surviving component of the `V1R-060` "Settings mapping complete" row (`TODO(20260818-163801).md:753`). The other three fields that row names — `volume`, `hide_delay_seconds`, `tts_model` — now have runtime consumers (§9).

**Required end state.** Either `min_cooldown_seconds` is exposed as a validated setting and mapped like its peers, or the row's annotation is corrected to record it as a deliberately fixed V1 policy constant with the rationale stated. Both outcomes are acceptable; leaving the row's annotation asserting a defect that was three-quarters repaired is not.

### 7.3 Stale defect annotations in the feature TODO — **S4**

`TODO(20260818-163801).md` carries prose annotations on unchecked rows describing defects found in the 2026-08-24 review. The P14–P20 remediation repaired many of them, but the annotations were not revised. The tracker therefore now under-reports in the same way it previously over-reported: a reader consulting it is told that working capabilities are broken.

Eight rows were verified against source during this review. Their current state is recorded in §9. Because these annotations were themselves the input to the prior remediation plan, leaving them stale risks a future cycle re-specifying work that is already done.

**Required end state.** Each row listed in §9 is corrected — checked where the criterion is now met, or re-annotated to describe only the portion that remains open. Every revision cites the source location that establishes it. The correction is a records change and must not be conflated with new implementation work.

## 8. Verified strengths — do not regress

Recorded so a later cycle does not undo them without noticing. Each was confirmed by sweep during this review.

- **Production Rust contains essentially no `.unwrap()` / `.expect()`.** A per-file count excluding `#[cfg(test)]` bodies found hits only in `desktop/macos/platform_application.rs:26-30` (five `CString::new` calls on string literals, infallible by construction) and `bin/export_frontend_contract.rs` (a build tool).
- **No `#[allow(...)]` or `#[expect(...)]` lint suppression exists in production source.** `V1R-004`'s claim holds under a repository-wide sweep.
- **`unsafe` is confined to eight files**, all genuine FFI boundaries: the three macOS platform observers plus `platform_prelude`, `asr/moonshine/ffi.rs`, `asr/runtime_metrics.rs`, `audio/permissions.rs`, and `asr/moonshine/installer/disk.rs`. No application-owned CPAL `unsafe impl Send` wrapper remains.
- **The Live-session delivery contract is documented at the API boundary.** `ai/google/live/session.rs:11-12` states in the code that `Ok(())` means acceptance into the bounded local outbound queue, not socket write or provider acknowledgement, and `outbound_diagnostics()` exposes delivery state. This resolves `V1R-142` more soundly than that requirement was originally written.
- **`handle_local_asr_event` re-validates identity after acquiring the session lock.** `conversation/session.rs:445-458` re-checks conversation state, generation, session id, and ASR mode immediately before the provider call, with the reasoning recorded in a comment.
- **`LocalAsrPipeline::stop_and_join`** (`asr/pipeline.rs:206-221`) performs a cooperative stop followed by `spawn_blocking(|| worker.join())`, which is the correct resolution of `V1R-144`'s original, impossible "join or abort the OS thread" requirement.
- **The Rust `#[cfg(test)]` mirror anti-pattern is closed.** Remaining `#[cfg(test)]` functions in production modules are legitimate test seams — constructors, accessors, and mock builders — not re-implementations of production logic.

## 10. Unverified and out-of-scope

Recorded so that a later reader does not mistake a hypothesis for a finding.

### 10.1 The mechanism of the §5.1 flake is not established

The `with_default` / global-interest-cache hypothesis in §5.1 is plausible and consistent with the observation that the test passes in isolation. It is **not confirmed**. A narrowed run restricted to `sensitive_asr_payloads`, `google_provider_failure_logging`, and the tool-router log test, with `--test-threads=8`, produced **0 failures in 12 runs** — it did not reproduce the flake. Either the interfering subscriber is one of the other four `capture_logs` call sites, or the mechanism is different from the hypothesis. §5.1's acceptance criterion is stated as a measured failure rate specifically so that it cannot be closed by acting on this hypothesis alone.

### 10.2 Non-macOS secret persistence

On non-macOS targets, `SecretStore::new` selects `MemorySecretBackend` (`src-tauri/src/secrets/store.rs:46`), so the Google API key does not survive process restart on Linux development builds. This is the correct fail-closed behavior — the alternative is plaintext on disk — and it is `#[cfg]`-gated away from macOS production. **Not a defect. Recorded only because it surprises developers on Linux.** No requirement follows.

### 10.3 Deferred to the existing product TODO

`TODO(20260818-163801).md` retains 163 unchecked rows, the large majority of which are manual, physical-device, macOS-hardware, signing, notarization, and clean-machine acceptance items. Those remain owned by that document and are untouched here. This specification adds no manual or physical acceptance obligation, and converts none of the existing ones into automated evidence.
