## 1. Purpose

A source-level code review conducted on 2026-08-28 against `HEAD = 55bcea5c`, together with an execution of the repository's canonical quality gate, produced eight confirmed defects. External review then contributed a ninth requirement and corrected three others. This document specifies the required end state for each.

The prior remediation cycle (P14–P20) repaired the defects it set out to repair. This cycle addresses a different and narrower class of problem: **the repository's own verification apparatus cannot currently be trusted to tell the truth about the repository.**

Three independent mechanisms were found, each of which causes a gate to report a result that does not correspond to the state of the code:

1. **The gate does not run.** `npm run check:all` exits non-zero on a clean checkout for reasons unrelated to the source under test (§4).
2. **The gate is nondeterministic.** `npm run check:rust` fails approximately one run in five, on a test whose failure carries no information about the code it names (§5).
3. **The gate tests a parallel implementation.** The entire frontend test suite exercises browser fallback mocks rather than the IPC boundary those mocks stand in for (§6).

The third mechanism is the same class of defect that `V1R-180` closed on the Rust side — a test that duplicates a production branch rather than calling it. It survived that remediation because `V1R-180` was scoped to `#[cfg(test)]` mirrors in Rust and the frontend equivalent is expressed differently: as a runtime environment check, not a compile-time attribute.

Every finding in this document was **verified against source or by measurement**, and each requirement cites its evidence. This document previously carried an unconfirmed hypothesis in §5.1; external review supplied the repository history that confirms it, and §5.1 is rewritten accordingly.

## 3. Severity model

This document retains the severity model established in `SPEC(20260824-142233).md` §3, with one clarification for this cycle's subject matter.

- **S1 — Correctness under concurrency or failure.** A race, panic, silent data loss, or stuck state that can occur in normal operation. Must be fixed before V1. **For this cycle, a gate that fails or flakes for reasons unrelated to the code under test is S1**, because it destroys the signal every other requirement in the repository depends on.
- **S2 — Privacy or test-integrity defect.** A privacy control whose enforcement is unproven, or a test that cannot fail when its production path regresses. Must be fixed before V1, because these defects hide other defects.
- **S3 — User-visible defect.** Incorrect or misleading behavior a user can observe, including accessibility barriers. Must be fixed before V1.
- **S4 — Structural.** Duplication, dead code, or record divergence that has not yet produced a user-visible defect but has already caused drift or blocks safe change. Fix before V1 where cheap; otherwise record an explicit deferral.

A requirement is complete only when its runtime behavior is correct **and** a test exercises the production path. A test that duplicates a production branch instead of calling it does not satisfy any requirement in this document.

**Additional closure rule for this cycle.** No requirement in this document may be closed on the basis of a green CI run alone, because §4 establishes that CI and a local clean checkout currently disagree. Closure evidence must state which environment produced it.

### 3.1 Product decisions settled before implementation

Two questions raised by external review were genuine product/repository policy decisions rather than technical findings. Both were settled by the project owner on 2026-08-28 and are binding on this specification.

1. **Generated dependency and build trees are untracked.** `node_modules/` and `dist/` are removed from version control and regenerated normally. `npm ci` is the canonical dependency materialization step. This supersedes the original §4.1/§4.2 design, which assumed the tracked tree would be preserved and made self-consistent.
2. **Ambient deduplication is event-fingerprint deduplication.** Semantic near-duplicate suppression of generated remark text is **not** a V1 requirement. `V1R-071`'s wording is narrowed to match the intended behavior and closed on current evidence, rather than left ambiguous or expanded into new implementation work.

A third question — whether browser-only `npm run dev` remains supported — is answered from existing documentation rather than by decision: `README.md:129-133` documents it as supported frontend-only development. §6.4 specifies how that is preserved without compromising test fidelity.

## 4. Gate executability (P21)

### 4.1 Tracked `node_modules/` has diverged from the lockfile — **S1**

**Corrected 2026-08-28.** The original requirement directed that the tracked tree be refreshed to match the lockfile, and §4.2 specified a drift verifier to keep it that way. External review observed that this institutionalizes a repository state that `CLAUDE.md` itself records as probably unintentional, and that no single committed tree can be a correct installation for every supported development host. Per §3.1 decision 1, the requirement is now satisfied by **removing** the tree, not by reconciling it. The defect analysis below is unchanged; only the prescribed end state moved.

This repository tracks `node_modules/` in git (12,845 files under `git ls-files node_modules`) and `dist/` (6 files). Commit `2d61e7b5` (`build: eliminate development dependency advisories`) upgraded the frontend toolchain in `package.json` and `package-lock.json`, and changed `vite.config.ts:26` to `minify: "oxc"`, but did not update the tracked `node_modules/` tree.

Measured divergence:

| Package | `package.json` | `package-lock.json` | Tracked `node_modules/` |
| --- | --- | --- | --- |
| `vite` | `^8.2.2` | 8.2.2 | **5.4.21** |
| `vitest` | `^4.1.11` | 4.1.11 | **2.1.9** |
| `@vitejs/plugin-react` | `^6.1.0` | 6.1.1 | **4.7.0** |
| `esbuild` | — | **absent** | **0.21.5** |

The tracked version is confirmed by `git show HEAD:node_modules/vite/package.json`, so this is committed state, not local drift.

Three consequences follow, each independently sufficient to require repair:

1. **The canonical gate does not run.** `npm run check:all` exits 2 at its first step:
   ```
   vite.config.ts(26,5): error TS2769: No overload matches this call.
     Type '"oxc"' is not assignable to type 'boolean | "terser" | "esbuild" | undefined'.
   ```
   `minify: "oxc"` requires Vite 7 or later. Vite 5 can neither type it nor execute it. `npm run build` fails identically. Three of the five frontend gate steps therefore cannot report on the source at all.

2. **CI and a clean checkout disagree.** Every CI job runs `npm ci` first (`.github/workflows/ci.yml:44,135,169,236`), which installs the lockfile tree and passes. A developer who clones the repository and runs the documented command in `AGENTS.md` gets a failure that has nothing to do with their change. The repository's stated verification workflow is not reproducible.

3. **`V1R-006` is not satisfied.** That task is recorded `[x]` in `TODO(20260818-163801).md:89-97` with implementation evidence asserting that the advisory-bearing development dependency chain was eliminated. `esbuild` 0.21.5 remains committed in the repository and is absent from `package-lock.json` entirely. CI's `npm audit` runs after `npm ci` and therefore never observes it. This is the single reopened item from a prior remediation cycle.

A fourth consequence is not a defect but must be recorded because it invalidates evidence: **the 64 frontend tests observed passing during review ran under Vitest 2.1.9**, not the 4.1.11 the project's records assert. Any prior claim of the form "the frontend suite passes" is evidence about a toolchain the project no longer declares.

**Supporting observation from external review, verified.** The tracked tree contains host-specific native packages — `@esbuild/linux-x64`, `@rollup/rollup-linux-x64-gnu`, `@tauri-apps/cli-linux-x64-gnu`, `@napi-rs/lzma-linux-x64-gnu`. A tree containing Linux-only binaries cannot be a canonical installation for the macOS hosts this product targets, which is independent evidence that the committed tree was never serving its apparent purpose.

**Required end state.** `node_modules/` and `dist/` are no longer tracked in version control and are ignored. `npm ci` materializes dependencies. `npm run check:all` completes every step after a normal `npm ci`, and `vite.config.ts:26` is valid for the installed Vite version. `V1R-006`'s claim is true of the resulting repository, or its record is corrected.

**Not in scope.** Whether any build output should be distributed by another mechanism is a packaging question owned by P13, not this document. Removing `dist/` from git does not change what the macOS bundle ships.

### 4.2 Generated trees must not silently return — **S2**

**Corrected 2026-08-28.** This section originally specified a verifier that compared the tracked `node_modules/` tree against `package-lock.json`, and required it to run in an environment that does not first overwrite the tree. Under §3.1 decision 1 there is no tracked tree to verify, so that requirement is void. What survives is the narrower obligation that the removal cannot silently undo itself.

The §4.1 divergence persisted across an entire remediation cycle without detection, because nothing observed the tracked tree — and CI could not, since `npm ci` replaces `node_modules/` before any check runs. Removing the tree eliminates that specific blind spot, but not the more general one: a future `git add -f`, a tooling change, or an over-broad `git add` can reintroduce either directory, and CI would again not notice.

**Required end state.** `.gitignore` covers both directories, and a check fails if either is reintroduced to the index. The check must not depend on the tree being present, and must not itself require `npm ci` to have run.

## 5. Gate determinism (P21)

### 5.1 `sensitive_asr_payloads_are_processed_without_entering_tracing` is nondeterministic — **S1**

**Measured:** 2 failures in 10 consecutive `cargo test --manifest-path src-tauri/Cargo.toml --all-features --lib` runs. The same test passes when run in isolation by name.

```
thread '...' panicked at src/asr/pipeline_tests.rs:552:5:
assertion failed: logs.contains("Local ASR inference worker started")
```

`npm run check:rust` is the declared source of truth for the Rust quality gate (`AGENTS.md`). It exits 101 on approximately one run in five for a reason unrelated to any change under test.

**Corrected 2026-08-28 — the mechanism is established, not hypothetical.** The original draft recorded a `with_default` / process-global-interest hypothesis and explicitly declined to treat it as a finding, because a narrowed reproduction had failed to confirm it. External review supplied the missing evidence: commit **`886de2b4f`** (`test: remove flaky tracing field assertions`, 2026-08-24) encountered this exact failure mode in `tools/router/tests.rs` and recorded the cause in the code that replaced it:

```rust
// Positive routing assertions use the structured audit rather than formatted
// tracing text. Tracing callsite interest is process-global, so parallel
// tests can legitimately suppress a callsite in this thread-local formatter.
```

That commit removed `assert!(logs.contains("remember_fact"))` and `assert!(logs.contains("Tool call rejected"))` and replaced them with assertions on `ToolAuditRecord` fields obtained from `router.audit_snapshot()`.

The mechanism is therefore: `capture_logs` (`src-tauri/src/test_support.rs:34-44`) installs a subscriber **thread-locally** via `tracing::subscriber::with_default`, while `tracing`'s callsite-interest cache is **process-global**. Under the parallel harness, a callsite can be cached as disabled by an unrelated concurrent subscriber, after which the thread-local formatter never sees it. The narrowed 12-run reproduction failed only because it did not include whichever concurrent test wins that race; it did not disconfirm the mechanism.

**This changes the prescribed repair.** The original TODO instructed that a positive control be added to `tools/router/tests.rs:249`. That is precisely the assertion `886de2b4f` deleted, and re-adding it would reintroduce a known flake. The correct pattern is the one that commit demonstrates: **prove the positive side from structured data, not from formatted tracing text.**

**Structural hazard, unchanged.** The failing assertion at `pipeline_tests.rs:552` is a positive control — it proves log capture was live before the test concludes anything from an absence. Whenever it breaks, the three privacy assertions after it pass **vacuously**; an empty log contains no transcript.

Six tests in the repository are privacy proofs of the form "sensitive value must not appear in logs." Four use `capture_logs`; two construct an equivalent subscriber inline. Half carry a positive control:

| Test site | Positive control | Form |
| --- | --- | --- |
| `asr/pipeline_tests.rs:511` | Yes — `:552` | **Log text** — this is the assertion that flakes |
| `desktop/runtime.rs:289` | Yes | **Log text** — `assert!(logs.contains("Desktop observer result"))` |
| `ai/google/auth.rs:92` (inline) | Yes | **Log text** — `assert!(logs.contains("Google provider failure"))` |
| `tools/router/tests.rs:249` (inline) | Yes, indirectly | **Structured** — `ToolAuditRecord` assertions, per `886de2b4f` |
| `character/prompt.rs:185` | **None** | Negative assertions only |
| `commands/conversation/tests.rs:73` | **None** | Negative assertions only |

Three controls are expressed as log-text assertions and are therefore themselves exposed to the mechanism above; only `tools/router/tests.rs` uses the robust form. Two tests have no control at all.

**Required end state.** `npm run check:rust` is deterministic. The stated acceptance is a measured failure rate, not a code change:

- The full Rust suite completes with 0 failures across at least 20 consecutive runs on the same commit.
- Every log-capture privacy test can prove capture was live, by a means not itself subject to callsite-interest suppression — structured data where available, following `886de2b4f`.
- No privacy assertion in the repository can pass against an empty captured log.

Serializing the affected tests is an acceptable fallback if scoped-dispatcher isolation cannot fully solve it, but weakening or deleting a privacy assertion to remove flakiness is not.

## 6. Test fidelity (P22)

### 6.1 The frontend suite never exercises the IPC boundary — **S2**

`src/lib/tauriBridge.ts` implements every backend call as a two-branch function:

```ts
async getMicrophonePermission(): Promise<MicrophonePermissionState> {
  if (!isTauri()) return "unavailable";
  const { invoke } = await import("@tauri-apps/api/core");
  return invoke<MicrophonePermissionState>("get_microphone_permission");
},
```

There are exactly forty such branches. `isTauri()` (`src/lib/tauriBridge.ts:30-35`) reads `window.__TAURI_INTERNALS__`.

**Nothing in `src/` ever sets `__TAURI_INTERNALS__`** — not `src/test/setup.ts`, not any individual test, not the Vitest configuration. The only occurrences of that identifier in the repository are its two uses inside `isTauri()` itself.

Therefore, in every frontend test:

- `isTauri()` returns `false`;
- every bridge method returns its browser fallback mock and returns **before** reaching `await import("@tauri-apps/api/core")`;
- because that import is inside the branch, the mocked module is never even loaded;
- the `vi.mock("@tauri-apps/api/core")` command dispatcher at `src/test/setup.ts:9-62`, which maps 15 command names to fixtures, is unreachable for every `tauriBridge` method;
- the `vi.mock("@tauri-apps/api/event")` listener stub at `src/test/setup.ts:64-68` is likewise unreachable, since `tauriBridge.ts:228` short-circuits with `return () => undefined`.

No test in `src/test/` asserts on `invoke` at all, so nothing detects this.

This is the frontend expression of the defect `V1R-180` closed in Rust: a test suite proving properties of a parallel implementation rather than of the production path. Every P11 and P12 frontend acceptance row in `TODO(20260818-163801).md` currently rests on this suite.

**Corrected 2026-08-28 — acceptance narrowed.** The original draft required that "a deliberate rename of a Rust `#[tauri::command]` causes a frontend test failure." External review correctly observed that the proposed mechanism cannot deliver this. Command names are hard-coded strings in `tauriBridge.ts`, and a mocked `invoke` dispatcher contains its own independent hard-coded copies. Renaming `get_settings` to `get_app_settings` in Rust leaves both TypeScript strings agreeing with each other, and the suite stays green. Cross-language contract integrity is a separate concern and is specified in §6.2.

**Required end state.** Frontend tests exercise the production branch of `tauriBridge` — the branch that resolves `invoke` — with `invoke` mocked at the module boundary. A test exists that fails if the suite silently reverts to the fallback branch. The browser fallback branch is governed by §6.4.

**Expected consequence, which is the finding.** Enabling the production branch is expected to break existing tests, because `src/test/setup.ts`'s dispatcher returns `null` for any command it does not enumerate and currently enumerates 15. That breakage is the previously hidden gap, not a regression introduced by the fix. Each resulting failure must be resolved by supplying a fixture that matches the Rust command's real signature — not by re-widening the fallback.

### 6.2 No cross-language command contract exists — **S2**

**Added 2026-08-28** at external review's recommendation, splitting the unachievable half of §6.1 into its own requirement.

The frontend invokes command names as string literals; Rust registers them in `tauri::generate_handler!` at `src-tauri/src/lib.rs:181-222`. Nothing connects the two. A rename, a signature change, or a removed registration is detectable only at runtime, in the packaged application.

The current state was verified during this review and is clean, which makes this the right moment to add the gate:

- the bridge invokes **37** distinct command names;
- **all 37** are registered in `generate_handler!`;
- five registered commands are not invoked from `tauriBridge.ts` — `dismiss_moose`, `show_moose`, `hide_moose`, `trigger_ambient_remark`, `get_live_outbound_diagnostics` — consistent with tray, menu, and backend-initiated paths rather than with drift.

No defect exists today. The defect is that nothing would report one.

**Required end state.** A check fails when a command name invoked by the frontend is not registered in Rust. It is satisfied by either generated IPC bindings emitted from the Rust command registry, or a CI verifier that extracts registered names and compares them against frontend usage or a shared manifest. Commands registered but not invoked from the bridge are reported informationally, not as failures, since backend-initiated commands are legitimate.

### 6.3 The generated backend contract has no drift gate — **S2**

`V1R-060`'s duplicated-defaults defect was repaired correctly in substance: the hand-maintained `AppSettings` blob in `src/lib/tauriBridge.ts` is gone, and `src/lib/backendContract.ts` now derives frontend defaults, the Google model catalog, and the TTS voice catalog from `src/generated/backendContract.json`, which is produced from Rust by `scripts/generate_frontend_contract.sh`.

The generated file is committed, and **nothing regenerates it and verifies it is unchanged**. The script is referenced only by `package.json:14` (`generate:frontend-contract`); it appears nowhere in `.github/workflows/`. `src/test/backendContract.test.ts` asserts internal consistency of the committed JSON — that default model ids appear in the committed catalog, that the voice list has 30 entries — but nothing compares it to Rust.

The divergence this closes can therefore silently return: a changed Rust default, model id, or voice list leaves the committed JSON stale, and the frontend continues to assert against the stale copy. The failure mode is identical to the original `V1R-060` defect; only its location moved, from a hand-written blob to a generated-but-unverified file.

**Required end state.** CI regenerates `src/generated/backendContract.json` from Rust and fails if the committed file differs. The check must fail when a Rust default is changed without regenerating.

### 6.4 Browser preview and test fidelity must be separated explicitly — **S2**

**Rewritten 2026-08-28.** This section previously argued that two fallback branches — `hasGoogleApiKey()` and `testAiConnection()` — were an S3 defect, and justified it partly on the claim that `hasGoogleApiKey()` gates onboarding. **That claim was wrong**, and contradicted this document's own §9. `src/stores/mooseStore.ts:273` sets `isOnboardingOpen` from `onboardingStatus.needs_acknowledgement`; `hasApiKey` is stored at `:269` and does not gate the modal. The stale rationale is withdrawn. External review also observed that the problem is broader than two examples and that the original prescription risked destroying a supported workflow.

Two distinct requirements were being conflated:

- **Test integrity** — tests must not pass because a fallback manufactured success in place of a real IPC contract.
- **Preview ergonomics** — `README.md:129-133` documents `npm run dev` as supported frontend-only development with Vite, where no Tauri backend exists.

Making all forty fallbacks throw would satisfy the first and destroy the second.

The synthetic-success surface is wider than originally stated. Verified examples in `src/lib/tauriBridge.ts`:

| Line | Operation | Fabricated result |
| --- | --- | --- |
| `:249` | `hasGoogleApiKey` | `true` — asserts a credential exists with no secure store consulted |
| `:255-257` | `testAiConnection` | `{ success: true, message: "Mock API connection successful!" }` |
| `:343` | `startConversation` | `"mock-sess-123"` — a fabricated session id |
| `:379` | `deleteMemory` | `true` — reports a persistence mutation that did not occur |
| `:397` | `sendTextMessage` | `` `Mock reply to: "${message}"` `` — a fabricated provider response |

ASR model installation and further persistence and provider operations fall in the same class; the full inventory is part of the required work rather than assumed complete here.

**Required end state.** An explicit policy separates the two modes:

1. Production-like tests run through the IPC branch (§6.1) and never observe a fallback.
2. Browser-preview behavior is provided by a clearly named, explicitly selected development adapter — not by implicit per-function branches keyed on ambient global state.
3. Read-only presentation defaults may return benign placeholder data where that is harmless to preview.
4. Operations claiming an external effect — credential state, provider connectivity, persistence mutation, conversation lifecycle, model installation — either fail closed when no backend exists, or execute only through the explicitly enabled development adapter.
5. Preview behavior has its own tests and is never counted as production contract coverage.

## 7. Runtime and record correctness (P23)

### 7.1 Settings persistence race discards in-flight continuous edits — **S3**

`src/stores/mooseStore.ts` writes settings by two paths with different ordering:

- `updateSettings` (`:276-280`) cancels any pending debounced write, awaits the IPC call, and **then** calls `set({ settings: newSettings })`.
- `updateSettingsContinuous` (`:282-289`) calls `set({ settings: newSettings })` immediately and schedules the persistence write 100 ms later (`CONTINUOUS_SETTINGS_WRITE_DELAY_MS`, `:18`).

`src/components/Settings/BehaviorTab.tsx` uses both on the same screen: checkboxes call `updateSettings`, while the Talkativeness slider (`:44-49`) and the maximum-comments-per-hour slider (`:69-75`) call `updateSettingsContinuous`.

Reachable interleaving:

1. The user toggles a checkbox. `updateSettings(A)` cancels any pending write and awaits the IPC round trip.
2. During that await, the user drags the Talkativeness slider. `set({ settings: B })` applies immediately; a write of `B` is scheduled.
3. The IPC call resolves. `set({ settings: A })` overwrites `B`. **The slider visibly snaps back to its previous position.**
4. 100 ms later the scheduled write persists `B`.

The end state is that the store displays `A` while the backend holds `B`. The UI and persisted settings disagree until the next explicit reload, and the user's slider movement appears to have been rejected while in fact it was saved.

**Corrected 2026-08-28 — invariant narrowed.** The original requirement stated that "the store's view of settings does not diverge from what was persisted." External review correctly observed that this is broader than a write-ordering fix can deliver, because a second divergence path exists independently of ordering; see §7.2. This section is narrowed to ordering, and the failure path is specified separately so neither is lost.

**Required end state.** Successful settings writes are ordered such that an older delayed write cannot overwrite newer state, and a continuous edit made during an in-flight discrete write is not discarded. A deterministic test exercises the interleaving at step 2 — not merely sequential calls. Continuous controls must remain immediate and must not persist every pointer movement.

### 7.2 Rejected settings writes leave the store optimistically wrong — **S3**

**Added 2026-08-28** at external review's recommendation, carrying the invariant removed from §7.1.

`scheduleContinuousSettingsWrite` swallows persistence failure (`src/stores/mooseStore.ts:40-43`):

```ts
void tauriBridge.updateSettings(pending).catch(() => {
  // The next explicit settings action or reload reconciles persistence. Keep
  // provider/backend error details out of the frontend console.
});
```

The optimistic value set at `:285` remains in the store. If the backend rejects the write — validation failure, secure-store unavailability, a persistence error — the user sees a setting that was never saved, with no indication. The comment's stated recovery ("the next explicit settings action or reload reconciles persistence") is true only if such an action occurs, and the next write will compute its payload from a store state the backend never accepted.

Keeping provider error detail out of the frontend is correct and must be preserved; silently discarding the *fact* of failure is the defect.

**Required end state.** A rejected settings write does not leave the store asserting a value that was not persisted. The chosen recovery — rollback, authoritative re-read, or a typed non-sensitive error surfaced to the user while the store reconciles — is tested. Subsequent writes must not compute their payload from a falsely assumed persisted base. No provider or backend error detail reaches the frontend console.

### 7.3 `min_cooldown_seconds` has no settings mapping — **S4**

`BehaviorConfig::min_cooldown_seconds` is initialized from the constant `V1_MIN_AMBIENT_COOLDOWN_SECONDS` (`src-tauri/src/character/personality.rs:80,92`) and consumed by the cooldown policy (`character/behavior.rs:133`, `character/cooldown.rs:200`). `AppSettings::apply_to_character_config` (`src-tauri/src/app/state.rs:186-201`) maps seven personality fields and five behavior fields; `min_cooldown_seconds` is not among them, and no corresponding field exists in `AppSettings`.

This is the sole surviving component of the `V1R-060` "Settings mapping complete" row (`TODO(20260818-163801).md:753`). The other three fields that row names — `volume`, `hide_delay_seconds`, `tts_model` — now have runtime consumers (§9).

**Required end state.** Either `min_cooldown_seconds` is exposed as a validated setting and mapped like its peers, or the row's annotation is corrected to record it as a deliberately fixed V1 policy constant with the rationale stated. Both outcomes are acceptable; leaving the row's annotation asserting a defect that was three-quarters repaired is not.

### 7.4 Stale defect annotations in the feature TODO — **S4**

`TODO(20260818-163801).md` carries prose annotations on unchecked rows describing defects found in the 2026-08-24 review. The P14–P20 remediation repaired many of them, but the annotations were not revised. The tracker therefore now under-reports in the same way it previously over-reported: a reader consulting it is told that working capabilities are broken.

**Amended 2026-08-28.** External review identified three further rows whose current status is misclassified — two that should be closed rather than left open, and one that requires a product decision rather than indefinite ambiguity. All three are folded into this requirement and recorded in §9.

**Required end state.** Each row listed in §9 is corrected — checked where the criterion is now met, marked not-applicable where policy makes it vacuous, or re-annotated to describe only the portion that remains open. Every revision cites the source location that establishes it. The correction is a records change and must not be conflated with new implementation work, and must not manufacture product scope from a misread criterion.

## 8. Verified strengths — do not regress

Recorded so a later cycle does not undo them without noticing. Each was confirmed by sweep during this review.

- **Production Rust contains essentially no `.unwrap()` / `.expect()`.** A per-file count excluding `#[cfg(test)]` bodies found hits only in `desktop/macos/platform_application.rs:26-30` (five `CString::new` calls on string literals, infallible by construction) and `bin/export_frontend_contract.rs` (a build tool).
- **No `#[allow(...)]` or `#[expect(...)]` lint suppression exists in production source.** `V1R-004`'s claim holds under a repository-wide sweep.
- **`unsafe` is confined to eight files**, all genuine FFI boundaries: the three macOS platform observers plus `platform_prelude`, `asr/moonshine/ffi.rs`, `asr/runtime_metrics.rs`, `audio/permissions.rs`, and `asr/moonshine/installer/disk.rs`. No application-owned CPAL `unsafe impl Send` wrapper remains.
- **The Live-session delivery contract is documented at the API boundary.** `ai/google/live/session.rs:11-12` states in the code that `Ok(())` means acceptance into the bounded local outbound queue, not socket write or provider acknowledgement, and `outbound_diagnostics()` exposes delivery state. This resolves `V1R-142` more soundly than that requirement was originally written.
- **`handle_local_asr_event` re-validates identity after acquiring the session lock.** `conversation/session.rs:445-458` re-checks conversation state, generation, session id, and ASR mode immediately before the provider call, with the reasoning recorded in a comment.
- **`LocalAsrPipeline::stop_and_join`** (`asr/pipeline.rs:206-221`) performs a cooperative stop followed by `spawn_blocking(|| worker.join())`, which is the correct resolution of `V1R-144`'s original, impossible "join or abort the OS thread" requirement.
- **The Rust `#[cfg(test)]` mirror anti-pattern is closed.** Remaining `#[cfg(test)]` functions in production modules are legitimate test seams — constructors, accessors, and mock builders — not re-implementations of production logic.
- **The frontend/Rust command surface is currently consistent.** All 37 bridge-invoked command names are registered in `generate_handler!`. §6.2 adds the gate that keeps it so.
- **`tools/router/tests.rs` already demonstrates the robust log-privacy test pattern.** Per `886de2b4f`, its positive assertions read structured `ToolAuditRecord` data rather than formatted tracing text, which is why it is the one such test immune to the §5.1 mechanism.
