# P1 — Installer Cancellation and Async Correctness

## LLMR-100 — Track truthful in-flight installer phase

- [ ] Replace “model ID -> cancellation token only” state with an in-flight record that includes current phase.
- [ ] Represent at least `downloading`, `verifying`, and `promoting` or equivalent explicit phases.
- [ ] Update phase atomically/consistently as the install advances.
- [ ] Keep cancellation token ownership in the same authoritative in-flight record.
- [ ] Ensure cleanup removes the in-flight record on success, failure, and cancellation.

**Acceptance**

- [ ] A status query while hashing reports `verifying`, not `downloading`.
- [ ] A status query during promotion reports a truthful active state.
- [ ] Restart/stale-partial behavior remains safe.

## LLMR-101 — Move artifact hashing off the async executor

- [ ] Isolate the large synchronous SHA/size verification loop in `spawn_blocking` or an equivalent blocking worker.
- [ ] Keep typed verification outcomes when crossing the blocking boundary.
- [ ] Do not move network async I/O into unnecessary blocking code.
- [ ] Keep memory usage bounded by streaming reads rather than loading the GGUF into memory.

**Acceptance**

- [ ] The async install future does not perform the full GGUF hash loop directly on its executor worker.
- [ ] Verification of the existing catalog artifacts remains streaming/bounded.
- [ ] Tests can deterministically pause verification without blocking the whole async test runtime.

## LLMR-102 — Make SHA verification cooperatively cancellable

- [ ] Pass cancellation state into the verification worker.
- [ ] Check cancellation once per bounded read chunk or equivalently often.
- [ ] Return a typed cancellation result distinct from hash/size/network failures.
- [ ] Check cancellation again after the blocking worker returns.
- [ ] Do not emit `installed` after a cancellation has been accepted for that operation.

**Acceptance**

- [ ] Cancel during hashing terminates without waiting for the entire artifact hash.
- [ ] No final model/valid marker remains from the cancelled operation.
- [ ] The user-visible state becomes truthfully non-installed/cancelled/failed according to the existing state model.

## LLMR-103 — Close the verification-to-promotion cancellation race

- [ ] Add a mandatory cancellation check after successful verification and before artifact promotion.
- [ ] Define cancellation semantics if cancellation races the final rename.
- [ ] Ensure a renamed artifact without a committed valid marker is not treated as installed.
- [ ] Ensure cleanup/restart logic removes or safely ignores any incomplete promoted artifact.
- [ ] Add equivalent protection before committing the install marker.

**Acceptance**

- [ ] A deterministic barrier test cancels after verification but before promotion and proves no valid install results.
- [ ] A deterministic barrier test covers the narrow promotion/marker boundary.
- [ ] A later explicit reinstall succeeds cleanly.

## LLMR-104 — Add complete installer cancellation end-state tests

Cover all meaningful phases:

- [ ] cancel during download;
- [ ] cancel after download before verify;
- [ ] cancel during verify;
- [ ] cancel after verify before promotion;
- [ ] cancel at promotion/marker boundary;
- [ ] cancel then reinstall successfully;
- [ ] duplicate cancellation remains safe/idempotent where appropriate.

**Acceptance**

For every accepted cancellation:

- [ ] final GGUF is absent or explicitly non-installed;
- [ ] no valid marker exists;
- [ ] staging state is cleaned up;
- [ ] status does not later become `installed` for the cancelled operation.
