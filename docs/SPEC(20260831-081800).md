# AI Talking Moose — Local LLM Provider Specification

**Document:** `SPEC(20260831-081800).md`
**Repository:** `ekkus93/ai-talking-moose`
**Status:** Proposed implementation specification
**Scope:** Add a CPU-friendly local text-generation provider alongside Google Gemini while preserving current Gemini Live voice behavior.

---

## 1. Purpose

AI Talking Moose currently supports Google Gemini-backed text generation and Gemini Live voice conversation, with Moonshine providing optional local ASR. This specification adds a first-class **local LLM text provider** so the Moose can generate ambient remarks and typed-chat replies without sending those prompts to a cloud LLM.

The first release of this feature is intentionally bounded. It does **not** replace Gemini Live voice conversation. Instead, it introduces the local model runtime, model lifecycle, provider selection, privacy semantics, validation, and UI needed for local text generation, while leaving the architecture ready for a later fully local voice pipeline.

The product goal is not to maximize benchmark intelligence. The target workload is short, personality-driven Talking Moose output. A sub-1B model is explicitly acceptable and preferred when it produces responsive CPU inference with a small download and memory footprint.

---

## 2. Product Goals

### 2.1 Primary goals

1. Allow the user to choose **Local** or **Google Gemini** independently for text generation.
2. Support multiple local GGUF models without hard-coding the application to a single model.
3. Provide one recommended small CPU-oriented default model suitable for the Moose.
4. Keep ambient remarks and typed-chat generation behind the existing provider-neutral `TextModel` abstraction.
5. Preserve current Gemini Live voice behavior in the initial local-LLM release.
6. Make local model installation, verification, selection, deletion, and runtime failures explicit and observable.
7. Never silently substitute Fake, Gemini, or another local model when the selected provider/model is unavailable.
8. Keep model files out of Git and outside the application bundle unless a future release explicitly chooses to ship one.
9. Preserve current privacy, memory, transcript-retention, prompt construction, character-state, and speech-delivery policies.
10. Keep the implementation ready for a later `Moonshine ASR -> Local LLM -> TTS` voice path.

### 2.2 Secondary goals

1. Permit additional built-in local model catalog entries later without changing provider architecture.
2. Permit a future custom GGUF import workflow.
3. Permit future runtime acceleration choices while keeping CPU-only execution a supported baseline.
4. Make model/runtime diagnostics sufficient to troubleshoot local inference without exposing prompt or transcript contents by default.

---

## 3. Explicit Non-Goals for Local LLM V1

The following are out of scope for the first implementation unless a task below explicitly promotes them:

1. Replacing Gemini Live voice conversation with local generation.
2. Local TTS.
3. Arbitrary user-supplied GGUF import.
4. GPU-specific acceleration controls.
5. Model fine-tuning, LoRA loading, or adapter management.
6. RAG/vector databases.
7. Long-document chat or very large context windows.
8. Tool calling through the local text model.
9. Automatically downloading a model without explicit user initiation.
10. Automatically falling back to a different provider/model after failure.
11. Shipping gated-license model weights inside releases.
12. Supporting every GGUF architecture that llama.cpp can theoretically load.

## 4. Current Architecture and Integration Boundary

### 4.1 Existing provider-neutral text abstraction

The Rust backend already exposes a provider-neutral text interface:

```rust
#[async_trait]
pub trait TextModel: Send + Sync {
    async fn generate(&self, request: TextRequest) -> Result<TextResponse, ProviderError>;
}
```

`GoogleTextModel` implements this trait. Ambient generation and typed `send_text_message` obtain a model through `AppState::get_text_model()`. This is the correct extension point for a local implementation.

The local LLM feature MUST preserve this abstraction rather than introducing provider checks at each caller.

### 4.2 Existing voice architecture

Voice conversation is provider-session-oriented. Even when Moonshine is selected for local ASR, finalized local transcript text is currently sent into the active Gemini Live session with `send_text_turn()`.

Therefore, these are distinct product paths:

**Local Text V1:**

```text
Ambient event -> prompt -> selected TextModel -> reply -> existing TTS path
Typed message -> prompt -> selected TextModel -> reply -> existing TTS path
```

**Later fully local voice:**

```text
Microphone -> Moonshine ASR -> Local LLM -> TTS -> speakers
```

The initial implementation MUST NOT pretend that selecting a local text model makes Gemini Live voice conversation fully local.

## 5. Provider Model

### 5.1 Separate text-provider selection

The existing generic `provider` string currently couples unrelated AI services and also participates in Fake-provider behavior. This must be replaced or migrated so text generation is selected independently.

The authoritative persisted text-provider concept should be an enum-like value with at least:

```text
google
local
```

`fake` remains a test implementation detail and MUST NOT be selected as an implicit production fallback.

A Rust enum is preferred:

```rust
pub enum TextProvider {
    Google,
    Local,
}
```

with serde `snake_case` persistence.

### 5.2 Provider-specific model selections

The settings schema should retain provider-specific model choices independently so switching providers does not erase the previous choice.

Recommended persisted fields:

```text
text_provider
google_text_model
local_text_model
```

The existing `text_model` field may be migrated into `google_text_model` during the settings-version migration.

The final schema MUST avoid making one field ambiguously contain either a Gemini model ID or a local catalog ID.

### 5.3 No silent fallback

If Local is selected and the model is missing, invalid, corrupt, unsupported, or fails to load, generation MUST fail closed with a safe, typed error.

If Google is selected and the API key is absent or invalid, generation MUST return a Google authentication/setup error.

Production code MUST NOT perform these substitutions:

```text
Google missing key -> FakeTextModel
Local missing model -> Gemini
Local load failure -> another local model
Gemini failure -> local model
```

A model/provider change requires an explicit user action or an explicit test-only injection.

## 6. Initial Runtime Choice

### 6.1 llama.cpp / GGUF

Local LLM V1 should use **llama.cpp-compatible GGUF inference**.

Reasons:

1. CPU inference is a first-class use case.
2. GGUF provides a standard artifact format for many small models.
3. Quantized models provide a practical download/RAM footprint.
4. The application can support multiple model families behind one runtime boundary.
5. The runtime has broad macOS CPU support, including Apple Silicon and Intel Macs.

### 6.2 Rust integration strategy

The implementation should hide the concrete llama.cpp binding behind an internal local-runtime interface. The rest of the application must not depend directly on binding-specific types.

Preferred shape:

```rust
trait LocalInferenceRuntime: Send + Sync {
    async fn load(...);
    async fn generate(...);
    async fn unload(...);
}
```

or an equivalent concrete runtime object hidden behind `LocalTextModel`.

The implementation MAY use a maintained Rust binding around llama.cpp or a carefully managed subprocess runtime, but the chosen mechanism must satisfy all acceptance criteria in this specification.

A subprocess design MUST NOT depend on an independently installed user `llama-cli` executable unless the product explicitly changes its packaging contract. A bundled/native library approach is preferred for a normal desktop-app experience.

### 6.3 Runtime ownership

Only one authoritative runtime manager should own loaded local models. Avoid loading the same GGUF anew for every generation call.

The manager should support:

- lazy load on first use;
- reuse across requests;
- unload when selected model changes or is deleted;
- bounded serialization of generation if the runtime/model is not safely concurrent;
- cancellation or bounded shutdown during application exit;
- no use-after-delete or use-after-switch races.

## 7. Initial Supported Models

### 7.1 Recommended first model

The first recommended catalog entry should be:

**SmolLM2-360M-Instruct, GGUF Q4_K_M**

Rationale:

- approximately 360M parameters;
- small enough for CPU-first use;
- suitable for short English instruction-following output;
- permissive licensing is preferable for an in-app catalog;
- small download/RAM footprint is aligned with a lightweight novelty desktop assistant.

The exact artifact repository, revision, filename, expected bytes, and SHA-256 MUST be pinned and independently verified during implementation. Do not copy transient `main` branch artifact URLs into production metadata without a pinned revision.

### 7.2 Second supported catalog model

A second built-in catalog entry should target:

**Qwen3-0.6B Instruct/Chat-capable GGUF Q4_K_M**, configured in non-thinking mode when the selected template/model supports that distinction.

The exact model variant must be chosen during implementation based on llama.cpp compatibility and authoritative artifact licensing/metadata.

### 7.3 Catalog policy

Every built-in model entry MUST declare:

- stable application model ID;
- display name;
- model family;
- parameter scale;
- quantization;
- artifact filename;
- pinned artifact revision;
- download source;
- expected byte count;
- SHA-256;
- license identifier/name;
- license/reference URL or packaged notice requirement;
- context limit used by the app;
- recommended generation defaults;
- minimum/runtime compatibility metadata if required.

Catalog metadata is authoritative. The UI must not infer installability from an arbitrary URL or filename.

## 8. Model Storage and Installer

### 8.1 Storage location

Local LLM weights must live under the application-managed data/model root, not the repository and not `src-tauri/resources` by default.

Recommended conceptual layout:

```text
<app-data>/models/llm/<model-id>/<revision>/<artifact>.gguf
```

The implementation should reuse the same app-data ownership principles used by the Moonshine installer.

### 8.2 Install lifecycle

Each catalog model should have explicit install state:

```text
not_installed
downloading
verifying
installed
failed
```

The exact enum may differ, but the UI and backend need a deterministic state machine.

### 8.3 Download requirements

Downloads MUST:

1. occur only after explicit user action;
2. use HTTPS;
3. write to a temporary/staging file;
4. enforce an expected maximum/declared size;
5. verify exact expected bytes where appropriate;
6. compute and compare SHA-256 before install;
7. atomically move the verified file into its final location;
8. remove or quarantine invalid partial data;
9. expose safe progress information;
10. support cancellation where practical;
11. never mark a model installed before verification succeeds.

### 8.4 Deletion

Deleting a model MUST:

- reject or safely coordinate deletion while that exact model is actively generating;
- unload the model first if loaded;
- remove only the catalog-owned model directory/artifact;
- update install state deterministically;
- preserve settings selection if desired, but expose it as unavailable rather than silently switching models; or explicitly change the setting with a user-visible action. The chosen behavior must be tested and documented.

### 8.5 Interrupted installs

Startup/model refresh must detect stale temporary downloads. Partial files must not be treated as valid models.

## 9. Local Text Model Behavior

### 9.1 Request mapping

`LocalTextModel` MUST implement the existing `TextModel` contract:

```rust
async fn generate(&self, request: TextRequest)
    -> Result<TextResponse, ProviderError>;
```

The implementation must map:

- `system_instruction`;
- `prompt`;
- `temperature`;
- `max_tokens`;

into the selected model's chat/template format and sampling configuration.

### 9.2 Chat templates

Do not manually invent prompt-control tokens in application call sites.

The runtime layer should apply the model's supported chat template, or the catalog must explicitly define the template strategy if llama.cpp cannot infer it safely.

Template failure is a model/setup error, not a cue to send a raw concatenated prompt silently.

### 9.3 Generation limits

CPU-first defaults should keep requests bounded.

Recommended initial application policy:

- local context target: approximately 4096 tokens unless model/runtime constraints require otherwise;
- typed response maximum: approximately 128–192 output tokens by default, even if the existing cloud caller currently allows more;
- ambient response maximum: preserve the existing ~60-token request;
- retain the existing ambient 320-character delivery bound;
- default temperature around existing personality-oriented values unless model-specific testing indicates a lower value is necessary.

The product should favor latency and concise personality over long-form reasoning.

### 9.4 Thinking/reasoning modes

For model families that support optional thinking/reasoning modes, the default Moose configuration should disable them for Local LLM V1 unless benchmarks show a clear product benefit.

No hidden chain-of-thought text may be displayed, persisted, spoken, or included in diagnostics.

### 9.5 Empty/invalid output

An empty model response is not success. Callers should receive a safe model/protocol error or the existing bounded empty-output behavior where explicitly designed.

The backend must never manufacture a successful Moose reply solely to hide a local inference failure.

## 10. Runtime Resource Policy

### 10.1 CPU baseline

CPU-only operation is an acceptance requirement.

The application must not require Metal/GPU acceleration for Local LLM V1, even if the chosen llama.cpp integration can use it opportunistically later.

### 10.2 Threading

The runtime should choose a conservative default based on available CPU parallelism and avoid monopolizing all host cores by default.

If a user-facing CPU-thread setting is not added in V1, document and test the automatic policy.

### 10.3 Memory

The selected model must be loaded lazily. The runtime should not load every installed model.

Switching models should release old model/context memory before or during loading of the replacement, with deterministic failure handling if unload/load fails.

### 10.4 Concurrency

Only one generation for a given local runtime/model should execute concurrently unless the implementation is explicitly safe and benchmarked otherwise.

Ambient generation and typed-chat generation must not corrupt shared inference state if requested at nearly the same time.

Requests should either serialize, be rejected with a defined busy policy, or use separate safe contexts. The behavior must be tested.

## 11. Settings Schema and Migration

### 11.1 Settings version

Adding separate provider/model fields requires a settings-version migration.

Migration must:

1. preserve existing Google behavior for existing users;
2. move the old `text_model` value into `google_text_model`;
3. initialize `text_provider` to `google` for existing profiles unless there is explicit prior local configuration;
4. initialize `local_text_model` to the recommended catalog model ID without pretending it is installed;
5. preserve all unrelated settings;
6. write a normalized migrated settings blob once;
7. be idempotent.

### 11.2 New-profile default

A product decision must be encoded explicitly and tested:

Recommended default for new profiles: **Local text provider**, with the recommended model selected but not silently downloaded.

If the product instead chooses Google as the new-profile default, the implementation must document why. In either case, onboarding/settings must accurately explain whether an API key or model download is required.

### 11.3 Runtime-sensitive settings coordination

Changing text provider or local text model while generation is in flight must have defined ordering.

A request that has already captured a settings snapshot may finish using that snapshot, but subsequent requests must use the newly persisted selection. Model unload/switch must not race active inference unsafely.

## 12. UI/UX Requirements

### 12.1 AI settings organization

The current Gemini-only AI tab should become provider-aware.

Recommended structure:

```text
Text Generation
  Provider: [Local | Google Gemini]

  Local selected:
    Local model: [SmolLM2 360M ...]
    Status: Installed / Not installed / Downloading / Error
    [Download] [Cancel] [Delete]
    [Test Local Model]

  Google selected:
    Google API key controls
    Gemini text model selector
    [Test Gemini Connection]

Voice Conversation
  Gemini Live model
  Existing ASR controls remain elsewhere as currently designed
```

The UI must not imply that Local text selection makes Gemini Live voice local.

### 12.2 Model catalog UI

For each local catalog entry show enough information to make the choice understandable:

- display name;
- approximate model size/download size;
- installed state;
- short suitability label such as "Recommended / smallest" or "Better quality / larger";
- license name where appropriate;
- model revision/version if useful for diagnostics.

Avoid benchmark-heavy UI in V1.

### 12.3 Test action

A local-model test should execute a tiny deterministic/low-cost generation using the selected installed model and return a safe success/failure result.

It must not require Gemini credentials or network access after the model is installed.

### 12.4 Error UX

Expose errors such as:

- model not installed;
- download failed;
- checksum mismatch;
- unsupported/corrupt GGUF;
- runtime initialization failed;
- generation failed;
- insufficient memory where detectable.

Messages should be actionable but must not expose private prompt contents.

## 13. Privacy and Network Semantics

### 13.1 Local means local for text generation

When `text_provider = local`, the text-generation request itself MUST NOT perform network I/O.

This includes:

- prompt text;
- system instruction;
- memories inserted into the prompt;
- ambient event summaries;
- typed user text;
- generated response.

Model installation is a separate explicit network action and may download the configured artifact.

### 13.2 Existing cloud voice disclosure

If Gemini Live remains selected/required for voice conversation, the UI/onboarding/privacy documentation must clearly distinguish:

- local text generation;
- local Moonshine ASR;
- cloud Gemini Live voice conversation;
- cloud Google TTS where applicable.

### 13.3 Logging

Production logs must not contain:

- user prompt text;
- system prompt text;
- memory contents;
- model output text;
- transcript text;
- API keys;
- local filesystem paths containing sensitive user-specific components when avoidable.

Allowed diagnostics include stable model ID, catalog revision, quantization, timing, token counts, and safe error category.

### 13.4 Network-denial tests

Tests must prove local generation succeeds with the repository's network-denial harness enabled once an in-memory/test runtime fixture is provided.

The local path must never call the Google client as fallback.

---

## 14. Error Model

Extend provider errors only if the current categories cannot express local failures safely.

Likely mappings:

- model not installed / bad selection -> `Setup` or `Model`;
- corrupt/unsupported model -> `Model`;
- runtime load/configuration failure -> `Setup` or `Internal` depending on cause;
- local generation failure -> `Model` or `Internal`;
- cancellation -> add a dedicated safe category only if product behavior needs to distinguish it.

Do not expose raw llama.cpp/binding error strings directly to the frontend without sanitization.

Structured internal diagnostics may retain non-sensitive technical details separately from user-visible messages.

---

## 15. TTS Interaction

Local LLM V1 changes text generation, not speech synthesis.

Generated local text should continue through the existing standalone speech controller and currently selected TTS implementation.

If Google TTS remains selected, a local text response may still be sent to Google for speech synthesis. The UI/privacy language must not call the entire response path "offline" unless both generation and TTS are local.

A future local-TTS phase may remove this cloud dependency.

---

## 16. Ambient Remarks

Ambient generation is an ideal initial local-model workload because it already:

- uses `TextModel`;
- requests only about 60 output tokens;
- caps delivery at 320 characters;
- has deterministic privacy gates before and after generation.

Local LLM integration must preserve both privacy checks and existing character-state/speech semantics.

Provider/model switching must not bypass the second delivery-time privacy gate.

---

## 17. Typed Conversation

`send_text_message` should continue to:

- normalize/bound input;
- apply memory privacy settings;
- build the same character system instruction;
- use the selected `TextModel`;
- emit/persist transcripts according to existing settings;
- invoke existing TTS/speech behavior;
- restore character state correctly on errors.

Local generation must not create a parallel typed-chat implementation.

For Local LLM V1, consider reducing local `max_tokens` from the current cloud-oriented 1024 request to a model-appropriate bounded policy while leaving Gemini behavior unchanged.

---

## 18. Voice Conversation Compatibility

### 18.1 V1 behavior

`start_conversation()` and the Gemini Live session remain cloud-provider behavior in the initial release.

Selecting `text_provider = local` MUST NOT accidentally cause `get_live_provider()` to instantiate a fake or unsupported local live session.

### 18.2 Future architecture seam

A future phase should introduce a provider-neutral turn-generation conversation path that can consume finalized ASR text and produce text/TTS locally.

Do not force `LocalTextModel` to implement `RealtimeConversationProvider` merely to satisfy the current Live-session architecture.

The later local voice design should reuse:

- Moonshine ASR;
- `TextModel`;
- existing prompt/memory policy;
- standalone speech/TTS controller;
- character lifecycle state machine.

## 19. Packaging and Build Requirements

1. The selected llama.cpp integration must build on supported macOS targets used by CI.
2. Required native libraries must be packaged reproducibly.
3. CI must not download LLM weights for ordinary lint/unit-test jobs.
4. Model weights must not be added to Git.
5. Release license/notice collection must include the runtime and any redistributed native dependencies.
6. If runtime compilation materially increases bundle size, record the delta in reconciliation evidence.
7. The application must run normally when no local model is installed.

## 20. Licensing Requirements

Before a model enters the built-in catalog:

1. confirm the model license permits the intended download/use/distribution workflow;
2. record model source and license metadata;
3. do not bundle weights unless distribution rights and notice obligations are explicitly satisfied;
4. prefer permissive catalog entries for the initial implementation;
5. preserve third-party runtime license notices in the release inventory.

The application may provide a download link to a model it does not redistribute only when the source and terms allow the intended automated retrieval.

### 21.1 Unit tests

Cover at minimum:

- settings migration;
- provider selection;
- no Fake fallback;
- catalog lookup;
- model install-state transitions;
- checksum mismatch;
- interrupted install cleanup;
- delete/unload coordination;
- request-to-runtime mapping;
- chat template selection/failure;
- generation output normalization;
- provider-safe error mapping;
- concurrent generation policy;
- provider/model switch ordering;
- local network-denial behavior;
- privacy-safe logging.

### 21.2 Runtime abstraction tests

Most CI tests should use a fake/in-memory `LocalInferenceRuntime` so they do not require a 250–500 MB model download.

The fake runtime must be explicit test injection, not a production fallback.

### 21.3 Integration smoke

Add a separately invoked local-LLM smoke/acceptance path that can run with a real pinned small GGUF when explicitly enabled.

The acceptance should verify:

- artifact installation and SHA verification;
- CPU model load;
- short prompt generation;
- non-empty bounded response;
- unload/reload;
- no network access during generation.

Do not make ordinary CI depend on third-party model-host availability unless an intentionally cached/pinned acceptance job is designed for that purpose.

### 21.4 Frontend tests

Cover:

- Local/Google provider switch;
- local model selector;
- not-installed state;
- download progress;
- cancel/failure state;
- delete flow;
- test-model result;
- Google API controls hidden/disabled appropriately when Local is selected;
- voice/Gemini Live settings remain understandable;
- no UI manufactured success on backend failure.

## 22. Performance Acceptance

Local LLM V1 should record real CPU measurements on at least one supported development/CI-class machine or supported Mac.

Measure:

- model file size;
- peak RSS or model-load memory delta;
- cold load time;
- time to first generated token if available;
- tokens/second for a short Moose prompt;
- end-to-end latency for a 60-token ambient request;
- unload time.

No universal hard throughput target is required initially, but the recommended default must be subjectively usable for short Moose replies on CPU and must not cause the UI/event loop to freeze.

Inference must run off the UI thread.

## 25. Security and Failure-Handling Rules

1. Model downloads use pinned metadata and integrity verification.
2. Path construction must prevent model IDs/filenames from escaping the model root.
3. Do not execute downloaded files as programs.
4. Do not dynamically load arbitrary native libraries from the model directory.
5. Treat GGUF as untrusted input to the extent practical; fail safely on parser/runtime errors.
6. No raw runtime panic should cross the Tauri command boundary.
7. No provider substitution on failure.
8. No prompt/output logging.
9. No network during Local generation.
10. Model deletion/switching must coordinate with active inference.
11. Settings persistence failures must use the existing reconciliation/ordering guarantees.

## 26. Proposed Module Layout

Exact names may vary, but responsibilities should remain separated.

```text
src-tauri/src/ai/
  traits.rs
  types.rs
  google/
  local/
    mod.rs
    catalog.rs
    installer.rs
    runtime.rs
    text.rs
    diagnostics.rs
```

Avoid growing `app/state.rs` into the implementation home for local inference. `AppState` should select/inject providers, not own download/runtime algorithms directly.

Frontend additions should likewise keep the AI settings view decomposed rather than placing model lifecycle logic directly in one large component.

## 27. Migration/Compatibility Requirements

1. Existing users remain on Google text generation after migration unless they explicitly change provider.
2. Existing Gemini text-model selection is preserved.
3. Existing API key stays in the secure credential store.
4. Existing Moonshine/Gemini Live ASR migration semantics are unchanged.
5. Existing saved transcripts and memory are unchanged.
6. Existing frontend generated contract must be extended and pass drift/shape gates.
7. Settings migration must be covered by Rust tests and frontend fixture updates.

## 28. Acceptance Criteria — Local Text V1

Local Text V1 is complete only when all of the following are true:

### Architecture

- [ ] A production `LocalTextModel` implements the existing `TextModel` trait.
- [ ] Google and Local text-provider selection is explicit and independent of Gemini Live/TTS.
- [ ] Production has no Google/Local -> Fake silent fallback.
- [ ] Local model/runtime responsibilities are modular rather than embedded in `AppState` or UI components.

### Model lifecycle

- [ ] At least SmolLM2-360M-Instruct Q4_K_M is represented by pinned, verified catalog metadata.
- [ ] At least one additional local model entry is supported or the catalog architecture is proven with a second test/catalog entry.
- [ ] Download, progress, cancellation, integrity verification, install, and delete behavior are implemented.
- [ ] Corrupt/partial model files cannot be reported as installed.

### Generation

- [ ] Ambient remarks can use the selected local model.
- [ ] Typed messages can use the selected local model.
- [ ] Local generation runs successfully with network denied after installation.
- [ ] Local generation preserves system prompt, memory privacy, output bounds, character state, transcript policy, and speech routing.
- [ ] No hidden reasoning text is surfaced.

### UI

- [ ] Settings expose Local/Google text provider selection.
- [ ] Local model install/select/delete status is usable.
- [ ] Google controls remain available when Google is selected.
- [ ] UI clearly states that Gemini Live voice remains cloud-based in this phase.

### Quality

- [ ] Rust format, Clippy with warnings denied, Rust tests, frontend typecheck/lint/format/tests, generated-contract checks, dependency audit, and supported macOS bundle jobs pass.
- [ ] CPU-only real-model smoke is recorded on a pinned model/revision.
- [ ] Performance/resource evidence is captured.
- [ ] Model/runtime licensing is included in the release notice process.
- [ ] No model weights are tracked in Git.

## 29. Future Phase — Fully Local Voice

A follow-up specification should implement:

```text
Microphone
  -> Moonshine local ASR
  -> provider-neutral finalized user turn
  -> Local TextModel
  -> existing/local TTS
  -> speakers
```

That phase should make the conversation manager capable of a text-turn/TTS pipeline without pretending a local model is a Gemini-compatible `RealtimeConversationProvider`.

Future work may include:

- local TTS;
- custom GGUF import;
- optional GPU/Metal acceleration;
- larger local models;
- provider-specific context/history management;
- local tool calling if justified;
- offline-first onboarding mode.

None of those future features should be required to ship Local Text V1.

---

## 30. Final Design Principle

The Moose should have an explicit, trustworthy answer to the question: **where is my text being generated?**

If the user selects Local, text generation stays local or fails. If the user selects Gemini, text generation uses Gemini or fails. The application must never hide a broken configuration by silently switching providers.
