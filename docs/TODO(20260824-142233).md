# P14 — Backend correctness and concurrency repair

## V1R-140 — Generation safety across await points — **S1**

`conversation/session/event_loop.rs`, `conversation/session.rs`

> **Design jointly with V1R-163.** This row specifies the *generation/session-identity invariant only*. It deliberately does **not** prescribe lock scope. `handle_local_asr_event` currently holds `operation_lock` across `send_text_turn().await` (`session.rs:346` → `:389`) — that is the exact granularity V1R-163 requires removed, so it must **not** be copied as the pattern here.

- [x] Tool-call response path validates generation immediately before the send is accepted.
- [x] Microphone-chunk forwarding path validates generation immediately before the send is accepted.
- [x] A stale handle cannot cross into a newly started session, by whatever mechanism V1R-163's lock design settles on.
- [x] No global `operation_lock` is held across provider/network I/O in the resulting design.
- [x] Deterministic test proves a stale-generation tool response cannot enter a newly started session.
- [x] Deterministic test proves a stale-generation microphone chunk cannot enter a newly started session in `GeminiLiveAudio` mode.

### Acceptance

- [x] Interleaving `stop_session`/`start_session` during an in-flight send cannot cross a session boundary.
- [x] The above holds without reintroducing an unbounded lock hold across network I/O.

Implementation evidence (2026-08-24): provider sends revalidate generation/session identity while holding the replaceable Live-session slot immediately before the bounded send. `connect()`, `close()`, and `interrupt()` execute outside `operation_lock`; a concurrent Stop invalidates generation and prevents a stale start/send from activating or crossing into a replacement session.

## V1R-142 — Outbound provider message durability — **S1**

`ai/google/live.rs`

> **Contract must be defined before implementation.** The current path is `caller → mpsc::Sender<Message> (live.rs:630) → supervisor → socket.send()`. The caller's `Ok(())` today means *accepted into the local channel*, not *written to the transport*. Surfacing a later socket error to the original caller therefore requires a contract change (per-message oneshot ack or an equivalent outbound-queue abstraction) — not merely a return-value change. Note that even transport-write success does not prove Gemini processed the message absent an application-level ack.

- [x] The meaning of `Ok(())` at the public Live-session API boundary is documented explicitly as one of: (a) accepted into a reliable local outbound queue, or (b) written to the websocket transport.
- [x] Explicit delivery states are defined (queued / written / retried / terminally failed).
- [x] A queued non-`Close` message discarded by `drain_disconnected_messages` is retried across reconnect or reaches a bounded terminal outcome.
- [x] Tool responses are retained across reconnect until a bounded terminal outcome, so a `functionCall` cannot be left silently unanswered.
- [x] A terminal delivery failure returns a typed error to whatever boundary the chosen contract makes responsible.
- [x] Dropped/retried/failed counts are observable in diagnostics.
- [x] Test covers message loss across a reconnect.
- [x] Timeout/cancellation semantics are consistent with V1R-163.

Implementation evidence (2026-08-24): `LiveSession::Ok(())` is defined as acceptance into the bounded local outbound queue. Reconnect never drains that queue; a frame whose WebSocket write fails is retained as the first post-reconnect retry. Reconnect exhaustion records terminal/drop outcomes and emits a typed `ProviderError` through `LiveServerEvent::Error`. Delivery counters are exposed by `get_live_outbound_diagnostics`, and explicit close uses a cancellation token so cancellation does not consume queued traffic.

## V1R-144 — ASR worker lifecycle — **S1**

`asr/pipeline.rs`, `asr/moonshine/runtime.rs`

> **Cooperative cancellation only.** The worker is a real OS thread (`pipeline.rs:16` imports `std::thread::JoinHandle`; `:94` holds `Option<JoinHandle<…>>`, reaped via `spawn_blocking(|| worker.join())`). Rust provides no safe forced abort of an arbitrary OS thread, and the worker may be inside a blocking native init call. This row must **not** be read as requiring forced termination.

- [x] Cancelling `start_architecture` while awaiting readiness leaves an identified owner responsible for the worker — ownership is retained, not detached.
- [x] Cancellation is signalled cooperatively.
- [x] When the native startup call returns, the worker observes cancellation, tears down the engine, and exits.
- [x] The worker remains joinable/reapable after a cancelled start.
- [x] Startup is bounded by a timeout where the native API permits a meaningful one.
- [x] `MoonshineStream::stop()` marks the stream stopped on error paths so `Drop` cannot call `stop_stream` twice.
- [x] Test covers cancel-during-readiness and post-cancel cleanup.
- [x] Test covers the error path through `stop()` followed by `Drop`.

Implementation evidence (2026-08-24): startup now owns the inference `JoinHandle` through an RAII guard until readiness succeeds. Cancellation or readiness timeout sets the cooperative stop flag and transfers the still-owned worker handle to a dedicated reaper thread; once a blocking native factory returns, the worker observes the flag, stops the engine, exits, and is joined. The caller-facing readiness wait is bounded (30 s production; shortened in tests) without claiming forced cancellation of native initialization. `MoonshineStream::stop()` clears its Rust started-state before the FFI stop call, so a native stop error is surfaced once and `Drop` only frees the stream rather than calling native stop twice. Deterministic tests cover cancelled readiness ownership/reaping, bounded readiness timeout cleanup, and stop-error followed by Drop.
