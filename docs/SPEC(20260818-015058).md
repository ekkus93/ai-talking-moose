# Talking Moose AI — Product & Technical Specification

**Document status:** Draft V0.1  
**Target platform:** macOS first  
**Application shell:** Tauri 2  
**Frontend:** React + TypeScript + Tailwind CSS  
**Backend/core:** Rust  
**Primary AI provider for V1:** Google Gemini APIs  
**Date:** 2026-08-17

---

## 1. Executive Summary

Talking Moose AI is a modern reimagining of the classic Macintosh desktop character concept: a deliberately low-resolution, slightly obnoxious, voice-interactive moose that lives on the user's desktop.

The product is not intended to be a conventional chat application with a cartoon skin. Its defining interaction model is ambient and character-driven:

1. The user uses the computer normally.
2. The Moose observes a small, explicitly permitted set of local events.
3. The Moose decides whether an event is worth reacting to.
4. If appropriate, it appears and says a short remark.
5. The user may ignore it, dismiss it, click it, or talk back.
6. A click or explicit interaction can transition into a real-time spoken conversation.
7. The Moose returns to an idle or hidden state afterward.

The application should preserve the charm of early Macintosh software through intentionally crude pixel graphics, low-frame-rate sprite animation, cheesy lip synchronization, dry humor, and short unsolicited interruptions.

AI capabilities are provided through a replaceable provider layer. Google is the initial provider. Gemini Live is the preferred V1 path for real-time speech conversations, while text generation and standalone TTS are used for ambient comments and non-live speech.

## 2. Product Vision

### 2.1 One-sentence vision

> A funny, low-resolution AI moose that feels like it actually lives in the computer.

### 2.2 Product principles

1. **Character first, assistant second.**
   - The Moose may be useful, but usefulness is not its primary personality.
   - It must not sound like customer support.
   - It should rarely ask generic assistant questions such as "How can I help?"

2. **Ambient, not demanding.**
   - The Moose should spend most of its time hidden or quiet.
   - Silence is an intentional behavior.

3. **Voice first.**
   - Spoken interaction is the primary conversational mode.
   - Text transcripts and speech bubbles support the voice interaction rather than replacing it.

4. **Deliberately retro.**
   - Pixel graphics, integer scaling, low animation frame rate, classic desktop-window styling, and imperfect lip sync are features.

5. **Local control and privacy.**
   - Desktop observation is opt-in and granular.
   - Raw screen contents are not collected by default.
   - The user can inspect, disable, or erase local memory.

6. **Provider independence.**
   - Google is the initial AI provider, not an architectural dependency.
   - ASR, LLM, TTS, and real-time conversation interfaces must be replaceable.

7. **Safe tool boundaries.**
   - The model never receives unrestricted OS access.
   - All actions pass through explicit Rust tools with validation and permission checks.

## 3. Goals

### 3.1 V1 goals

V1 SHALL provide:

- A native-feeling macOS Tauri application.
- A small Moose window with original low-resolution artwork.
- Idle, blink, listening, thinking, speaking, sleeping, and annoyed animation states.
- Integer-scaled pixel rendering.
- A speech bubble/transcript UI.
- Microphone capture and audio playback implemented in Rust.
- Real-time voice conversation using Google Gemini Live.
- User interruption/barge-in while the Moose is speaking.
- Standalone ambient comments generated with a Gemini text model.
- Standalone TTS for ambient comments.
- A distinctive "old cartoon moose" voice direction without cloning Bullwinkle or a specific actor.
- Basic local memory.
- A settings window.
- A menu-bar/system-tray control.
- Opt-in ambient behavior based on low-risk local events.
- Secure storage of a user-supplied API credential.
- A provider interface that can support non-Google providers later.
- Automated unit, integration, lint, format, and frontend tests.
- macOS packaging suitable for local distribution.
- Clear privacy controls and a "Forget Everything" action.

### 3.2 Later goals

Post-V1 MAY include:

- Wake-word detection.
- Optional transparent/floating-character builds.
- Richer desktop context.
- Screenshot or vision understanding with explicit permission.
- Calendar, weather, files, browser, or other tools.
- Voice cloning from an authorized original voice actor.
- Windows and Linux support.
- Multiple characters/personalities.
- Plugin/tool marketplace.
- Local/offline ASR, LLM, or TTS providers.
- Optional cloud synchronization of preferences or memories.
- User-created personalities and sprite packs.

## 4. Non-goals for V1

V1 SHALL NOT require:

- A wake word.
- Continuous microphone recording while the Moose is hidden.
- Full-screen capture.
- OCR of desktop contents.
- Reading arbitrary user files.
- Sending clipboard contents to the model by default.
- Autonomous shell command execution.
- Arbitrary model-generated code execution.
- A browser extension.
- A cloud account.
- A hosted service.
- Voice cloning of Bill Scott, Bullwinkle, or any recognizable third-party character voice.
- Exact reuse of copyrighted Talking Moose or Bullwinkle visual assets without a license.
- Mac App Store release as a launch requirement.

## 5. Target User Experience

### 5.1 First run

1. User launches Talking Moose AI.
2. A small retro Moose window appears.
3. Moose performs a short non-AI canned greeting.
4. The app opens onboarding.
5. User chooses:
   - microphone permission,
   - Google API authentication method,
   - whether unsolicited comments are enabled,
   - basic frequency,
   - whether local memory is enabled.
6. The app validates the AI connection.
7. User can click the Moose and speak.

### 5.2 Normal interaction

Default behavior:

- Moose is hidden or idle most of the time.
- User clicks Moose.
- Moose enters `LISTENING`.
- Audio is streamed to the real-time provider.
- Moose enters `THINKING` when appropriate.
- Moose speaks the response.
- Mouth animation follows output audio.
- User may interrupt.
- Conversation continues until:
  - timeout,
  - explicit dismissal,
  - user says goodbye,
  - fatal provider/audio error.

### 5.3 Ambient interaction

Example:

1. User rapidly alternates between Terminal and VS Code.
2. Desktop event aggregator records only permitted metadata.
3. Behavior engine evaluates:
   - recency,
   - repetition,
   - cooldown,
   - quiet hours,
   - annoyance budget,
   - whether a comment was recently made.
4. Behavior engine decides `speak = true`.
5. Text model generates a one-line observation.
6. Policy filter validates the utterance.
7. TTS generates audio.
8. Moose appears, speaks, waits briefly, and disappears.

### 5.4 Barge-in

If the user starts speaking while Moose is speaking:

1. Playback SHALL stop quickly.
2. Queued speech audio SHALL be discarded.
3. Character state becomes `INTERRUPTED` then `LISTENING`.
4. The real-time session SHALL preserve conversational context.
5. Moose MAY respond to the interruption in character.

### 5.5 Dismissal

The following should immediately stop an ambient utterance:

- close/dismiss UI action,
- configurable keyboard shortcut,
- "stop",
- "shut up",
- equivalent recognized intent.

Dismissal must not be treated as an application error.

## 6. Visual Design

### 6.1 Artwork

Artwork SHALL be original unless separately licensed.

Preferred source resolution:

- 64×64, 96×96, or 128×128 sprite cells.

Rendering requirements:

- nearest-neighbor/integer scaling,
- no smoothing,
- no vector redraw,
- no interpolation blur,
- deliberately limited animation frame rate,
- minimal palette,
- strong silhouette and exaggerated antlers.

### 6.2 Animation target

Typical animation cadence:

- idle: 2–4 FPS or event-driven frames,
- speaking: 4–8 FPS,
- blink: discrete frame sequence,
- transitions: intentionally simple.

The frontend SHALL not interpolate between sprite frames.

### 6.3 V1 Moose window

Default V1 uses a small decorated or custom-retro rectangular window rather than relying on transparent webview behavior.

Desired properties:

- small footprint,
- optionally always on top,
- movable,
- remembers position,
- does not steal focus for unsolicited comments when possible,
- accessible through menu bar/tray.

### 6.4 Optional future transparent mode

A transparent character-only window may be offered in a separately packaged build if platform/distribution constraints are acceptable.

### 6.5 Settings UI

Settings may look modern and use Tailwind normally. The retro visual constraint applies primarily to the character window.

## 7. Voice and Personality

### 7.1 Voice direction

The initial Moose voice SHALL be an original synthetic voice direction, not an attempt to reproduce a specific actor.

Target qualities:

- adult male-coded voice,
- medium to medium-low pitch,
- nasal resonance,
- mildly gravelly,
- slow or lumbering cadence,
- warm,
- slightly dim-witted delivery,
- dry timing,
- exaggerated old-cartoon phrasing,
- occasional puzzled pauses.

Example voice direction:

> Speak as a goofy, good-natured, slightly dim-witted old cartoon moose. Use a warm, nasal, mildly gravelly voice, rounded vowels, a slightly slow lumbering cadence, dry pauses, and occasional puzzled delivery. Do not imitate a particular actor or copyrighted character.

### 7.2 TTS candidates

The Google TTS voice and model SHALL be configuration values.

V1 SHOULD support auditioning at least three Google voices with the same test corpus before a default is selected.

### 7.3 Speech rules

Default character speech SHOULD:

- prefer 1–3 sentences,
- prefer observations over offers to help,
- avoid long lists unless explicitly requested,
- avoid repetitive catchphrases,
- avoid generic assistant language,
- permit comic hesitation and deadpan timing,
- remain intelligible,
- respect explicit user requests to be serious.

### 7.4 Personality controls

User-adjustable controls MAY include:

- sarcasm,
- friendliness,
- weirdness,
- talkativeness,
- helpfulness,
- verbosity.

The settings map to a normalized internal range, for example `0.0..=1.0`.

### 7.5 Character policy file

Personality configuration SHOULD be data-driven, for example YAML:

```yaml
identity:
  name: Moose
  species: moose

personality:
  dry: 0.90
  sarcastic: 0.70
  friendly: 0.55
  absurd: 0.65
  helpful: 0.35

speech:
  max_sentences_ambient: 2
  max_sentences_conversation_default: 4
  avoid_assistant_language: true
  allow_self_deprecating_humor: true

behavior:
  unsolicited_comments: true
  quiet_hours_enabled: true

rules:
  - Sometimes say nothing.
  - Prefer observations over generic offers of assistance.
  - Do not claim to have observed information the application did not provide.
  - Do not impersonate a real person or copyrighted character voice.
```

## 11. AI Provider Abstraction

### 11.1 Required logical interfaces

The Rust backend SHALL define interfaces equivalent to:

```rust
trait TextModel {
    async fn generate(&self, request: TextRequest) -> Result<TextResponse>;
}

trait SpeechSynthesizer {
    async fn synthesize(&self, request: TtsRequest) -> Result<AudioStream>;
}

trait RealtimeConversationProvider {
    async fn connect(&self, config: LiveSessionConfig) -> Result<LiveSession>;
}
```

A standalone ASR interface MAY be included even if V1 conversation ASR is supplied through Gemini Live:

```rust
trait SpeechRecognizer {
    async fn transcribe(&self, audio: AudioInput) -> Result<Transcript>;
}
```

### 11.2 Provider configuration

No business logic may depend on a literal Gemini model identifier.

Configuration SHALL contain aliases such as:

```toml
[ai]
provider = "google"

[ai.google]
live_model = "..."
text_model = "..."
tts_model = "..."
tts_voice = "..."
```

### 11.3 Google V1 mapping

Preferred V1 mapping:

- **Real-time conversation:** Gemini Live audio-to-audio model.
- **Ambient decision and short remarks:** Gemini text generation.
- **Ambient speech:** Gemini TTS.
- **Tool use:** Gemini function calling through the Rust tool router.
- **Authentication:**
  - local/BYOK development: user-supplied key stored securely;
  - later hosted distribution: short-lived/ephemeral client authorization through a service controlled by the project.

All preview model identifiers SHALL be replaceable through configuration.

### 12.2 Character states

Minimum V1 character states:

```rust
enum CharacterState {

    Appearing,
    Idle,
    Listening,
    Thinking,
    Talking,
    Interrupted,
    Annoyed,
    Sleeping,
```

### 12.3 Session behaviors

The real-time conversation layer SHALL:

- connect asynchronously,
- report state changes,
- stream audio with bounded buffers,
- expose input/output transcripts when available,
- support cancellation,
- handle model-side interruption events,
- stop local playback on interruption,
- handle reconnection cleanly,
- distinguish recoverable and fatal failures,
- never block the UI event loop.

## 13. Audio Architecture

### 13.1 Rust ownership

Audio capture and playback SHALL be implemented in Rust.

Suggested components:

- `cpal` for audio device access,
- a resampler such as `rubato` if needed,
- bounded lock-free or low-contention queues where practical,
- explicit audio format conversion.

### 13.2 Pipeline

Input:

```text
Microphone
  ↓
Native device format
  ↓
Convert to mono
  ↓
Resample as required by provider
  ↓
PCM framing
  ↓
Live provider
```

Output:

```text
Live/TTS provider
  ↓
PCM/audio decoder if required
  ↓
Playback queue
  ↓
Output device
  ↓
RMS/envelope analysis
  ↓
Mouth animation events
```

### 13.3 Lip synchronization V1

V1 lip sync SHALL be amplitude/envelope based.

Example mouth states:

```rust
enum MouthShape {
    Closed,
    Small,
    Medium,
    Wide,
}
```

Mouth state SHALL be derived from short windows of outgoing audio with hysteresis/smoothing to prevent excessive flicker.

Phoneme/viseme synchronization is deferred.

### 13.4 Audio failure requirements

The application SHALL handle:

- microphone missing,
- microphone permission denied,
- output device missing,
- device removed mid-session,
- sample-rate mismatch,
- buffer underrun/overrun,
- provider disconnect,
- malformed audio frame.

Errors SHALL be surfaced in the settings/troubleshooting UI without crashing the character window.

## 14. Ambient Behavior Engine

### 14.1 Purpose

The behavior engine decides **whether** Moose should speak. The LLM decides **what** to say only after the behavior engine permits speech.

### 14.2 Inputs

V1 inputs MAY include:

- current time,
- idle duration,
- time since last Moose utterance,
- time since last user interaction with Moose,
- repeated app-switch patterns,
- battery state,
- sleep/wake events,
- configured quiet hours,
- user-defined talkativeness.

### 14.3 Required guardrails

The engine SHALL enforce:

- minimum cooldown,
- per-hour utterance budget,
- quiet hours,
- recent-dismissal suppression,
- no repeated reaction to the same event,
- no overlapping ambient comments,
- no ambient speech during active conversation,
- mute state,
- full ambient-disable setting.

### 14.4 Decision model

The first decision layer SHOULD be deterministic where possible.

Optional low-cost model classification MAY produce:

```json
{
  "speak": true,
  "importance": 0.41,
  "mood": "amused",
  "topic": "repeated app switching"
}
```

The model's `speak` result SHALL NOT override hard local cooldown/privacy rules.

### 14.5 Annoyance budget

Maintain a rolling score representing how much unsolicited behavior has occurred.

The score increases on:

- unsolicited speech,
- repeated appearances,
- user dismissal,
- interruption.

The score decays over time.

The behavior engine SHALL suppress ambient activity above a threshold.

## 15. Desktop Awareness

### 15.1 V1 default permissions

Allowed with explicit setting:

- active application identity/name,
- application-change event,
- sleep/wake,
- battery level,
- system idle duration,
- network availability state.

Not enabled by default:

- window title.

Not V1 default:

- screenshots,
- screen OCR,
- clipboard,
- file contents,
- browser history,
- keystroke logging.

### 15.2 Data minimization

Desktop events SHALL be normalized into minimal semantic events before they are supplied to AI.

Example:

```json
{
  "type": "application_switch_pattern",
  "applications": ["Terminal", "Visual Studio Code"],
  "switch_count": 7,
  "window_seconds": 120
}
```

Do not send raw OS event streams when a summarized event is sufficient.

## 17. Memory

### 17.1 Local storage

Use SQLite for structured application data.

Suggested tables:

- `settings`
- `conversation_sessions`
- `conversation_turns`
- `memories`
- `observations`
- `ambient_actions`
- `tool_audit`
- `schema_migrations`

### 17.2 Memory classes

Memory SHALL distinguish:

1. **Preferences**
   - explicit user settings.

2. **User-approved semantic memories**
   - facts the user asks Moose to remember.

3. **Short-lived observations**
   - app/event summaries used for ambient behavior.

4. **Conversation summaries**
   - optional compact summaries for continuity.

### 17.3 Retention

Defaults:

- raw audio: never persisted,
- raw microphone frames: memory only,
- provider transient data: not intentionally cached,
- ambient observations: short retention,
- explicit memories: retained until removed,
- transcripts: configurable,
- conversation summaries: configurable.

### 17.4 Forget Everything

"Forget Everything" SHALL:

- remove local memories,
- remove stored transcripts,
- remove observations,
- remove conversation summaries,
- optionally remove provider credentials if user selects full reset.

Deletion SHALL be testable.

## 18. Secrets and Authentication

### 18.1 V1 BYOK

For developer and early-user builds:

- user supplies a Google API key,
- credential is handed to Rust through a Tauri command,
- credential is stored using a secure native/Tauri secret mechanism such as Stronghold,
- credential is never written to frontend localStorage,
- credential is never logged,
- frontend receives only masked/boolean credential state.

### 18.2 Distributed build

A future hosted configuration SHOULD avoid embedding a universal project API key in the app.

Preferred pattern:

```text
App
  ↓ authenticated request
Project token broker
  ↓
short-lived/ephemeral authorization
  ↓
App ↔ Google real-time service
```

### 18.3 Logging

Logs SHALL redact:

- API keys,
- authorization headers,
- ephemeral tokens,
- raw audio,
- private transcripts unless explicit diagnostic mode is enabled.

## 22. Privacy and Safety Requirements

1. Microphone use SHALL be visually indicated.
2. Continuous hidden microphone capture SHALL be off in V1.
3. Desktop-observation permissions SHALL be individually configurable.
4. No keystroke logger SHALL exist.
5. No arbitrary shell execution SHALL exist.
6. Screen capture SHALL not be silently enabled.
7. Raw audio SHALL not be persisted by default.
8. Users SHALL be able to disable all unsolicited comments.
9. Users SHALL be able to disable memory.
10. Users SHALL be able to erase stored data.
11. Prompt construction SHALL accurately distinguish observed facts from inferred context.
12. Tool calls SHALL be permission checked in Rust.
13. The model SHALL not be trusted as an authorization mechanism.

## 24. Performance Targets

Initial targets, subject to measurement:

- UI startup should feel immediate on a modern Mac.
- Moose sprite animation should consume negligible CPU while idle.
- Hidden state should minimize wakeups.
- Audio queues must be bounded.
- Barge-in should stop local playback perceptibly quickly.
- Ambient event aggregation should not poll at unnecessarily high frequency.
- Database work must not block real-time audio paths.
- Provider network I/O must not block Tauri UI threads.

No hard latency SLA is required until real hardware measurements exist.

## 31. Initial Acceptance Criteria

The first "real Moose" release is accepted when all of the following work on macOS:

1. App launches and displays the low-resolution Moose.
2. Moose can be moved and restores its position.
3. Moose animates idle/blink/talk states.
4. Settings window can be opened from menu bar/tray.
5. Microphone permission can be requested and diagnosed.
6. User can select input/output devices.
7. User clicks Moose to begin a Gemini Live conversation.
8. User speech is received by the provider.
9. Moose speech is played through the selected output.
10. Mouth animation follows output audio.
11. User can interrupt Moose during speech.
12. User can dismiss/end the session.
13. Ambient comments can be enabled.
14. Ambient comments obey cooldown and quiet-hour policy.
15. Moose can make at least one context-based observation using a permitted local event.
16. Google credential is not exposed to frontend storage/logs.
17. Basic local memory works.
18. "Forget Everything" removes retained local conversational data.
19. Normal test/lint/build suite passes.
20. The app remains usable if Google is unavailable; it shows a clear error and does not crash.

## 32. Deferred/Open Decisions

These decisions do not block implementation of the architecture:

### O-001 — Final Moose artwork

Default: commission/create original black-and-white or low-color pixel sprites inspired by early Macintosh aesthetics.

### O-002 — Final TTS voice

Default: audition multiple Google voices with the project voice-direction prompt. Do not clone Bullwinkle/Bill Scott.

### O-003 — Transparent overlay

Default: no transparent overlay in V1. Revisit after core UX is proven.

### O-004 — Hosted authentication

Default: BYOK for early builds. Add token broker only when distribution requirements justify it.

### O-005 — Window title observation

Default: disabled. Add only as explicit opt-in.

### O-006 — Transcript retention

Default: configurable; conservative default is limited local retention or off until product testing establishes value.

### O-007 — Embeddings/vector memory

Default: not required for first implementation. Begin with SQLite + recency/tag retrieval.

### O-008 — Wake word

Default: deferred.

### O-009 — Cross-platform

Default: macOS first; preserve portable abstractions where inexpensive.

## 33. Recommended Implementation Sequence

1. Tauri/React/Rust skeleton.
2. Moose window and sprite state machine.
3. Settings/menu-bar shell.
4. Rust audio capture/playback.
5. Fake/local conversation provider for deterministic testing.
6. Google authentication/configuration.
7. Gemini Live integration.
8. Barge-in.
9. Speech transcription UI.
10. Standalone Gemini text/TTS path.
11. Ambient behavior engine.
12. Basic desktop events.
13. Memory.
14. Tool calling.
15. Hardening, privacy, packaging.
16. Voice/art polish.

This ordering keeps each milestone demonstrable and avoids coupling the visual character to live network availability.

## 34. Product Litmus Test

Before accepting a new feature, ask:

> Does this make the Moose feel more like a character living in the computer, or merely make it more like a generic AI assistant?

If the answer is the latter, the feature should be reconsidered, hidden behind explicit interaction, or implemented in a way that preserves the character-first experience.
